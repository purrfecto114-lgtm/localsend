## §1 ROM 省电策略：持锁后组播到达率的真实差异

### 1.1 锁到底改变什么（作用域界定）`[AOSP源码]`

- `WifiMulticastLockManager.acquireLock()`（packages/modules/Wifi main, service/.../WifiMulticastLockManager.java:222-244）唯一动作：经 **primary ClientModeManager（STA）** 的 `FilterController.stopFilteringMulticastPackets()` 关闭 Wi-Fi 芯片的多播地址过滤，并做 BatteryStats/StatsLog 记账。
- 它 **不是** wake lock：不阻止 Doze、不阻止进程冻结（cached apps freezer）、不阻止 ROM 的后台联网策略。任何一层拦截都在锁的能力之外。

### 1.2 AOSP 版本分水岭：Android 16 引入「后台实效化」`[AOSP源码，决定性发现]`

对 `WifiMulticastLockManager.java` 逐 tag 比对（android.googlesource.com）：

| Android 版本 | uid importance 门控 |
|---|---|
| 12.0.0_r1 / 13.0.0_r1 / 14.0.0_r1 / **15.0.0_r1** | **无**（acquireLock 后无论 app 前后台，锁持续生效） |
| **16.0.0_r1 / main** | **有**：`IMPORTANCE_THRESHOLD = IMPORTANCE_CACHED`，注册 `OnUidImportanceListener`；持锁 uid 退成 cached 进程 → 锁挪入 inactive → 无 active 持锁者时系统重新开启过滤（`handleImportanceChanged`，main 分支 :75-88/:144-170） |

推论：
- **Android ≤15（当前存量主体）**：用户按 home / 锁屏（Activity stopped 未 destroy）→ **锁仍生效，组播持续到达**（前提：未进 Doze 深度期、进程未被冻结/断网）。收益与电池代价同时持续。
- **Android 16+**：同样的操作后系统自动恢复过滤 → 锁的实际有效期 ≈「app 处于前台/可见期」。电池代价被系统收敛，但「锁屏挂机接收」也随之失效。
- 生命周期错配事实：`onDestroy`（back 退出）释放锁时，LocalSend 的 server 与 discovery listener 仍在进程内运行（`init.dart:224-233` postInit 即启动且无 Stop 调用，全仓核实）→ back 退出后组播监听「聋」但 HTTP server 仍可被 /24 扫描发现 `[推演]`。

### 1.3 屏幕关闭 / Doze 下的投递（如实降级预期）

- **802.11 省电（非 Doze）**：STA 省电模式下 AP 将组播/广播帧缓存至 DTIM beacon 再发 `[文档]`（TP-Link AP 文档："When the access point has buffered broadcast or multicast messages for associated clients, it sends the next DTIM"）。锁关闭的是 STA 侧硬件多播地址过滤，**不改变 DTIM 行为** → 屏幕关后组播仍投递但带 DTIM 周期级延迟（通常数百 ms～秒级，取决于 AP 的 DTIM interval）`[推演]`。
- **Doze 深度期**（屏幕关 + 静止，约 30 分钟后逐级加深）：Doze 在维护窗口外切断 app 网络访问 `[文档]`（developer.android.com Doze 模式；佐证：issuetracker 37077627 显示 Doze 下连 WiFi 自动连接都被抑制）。**持锁不能克服 Doze**——深度 Doze 中 LocalSend 无法及时收组播，也响应不了 /24 扫描的 TCP probe（进程被冻结后 socket 缓冲堆积）`[推演]`。
- **结论（必须降级的预期）**：锁保证的只是「Wi-Fi 芯片不再过滤组播帧」；「亮屏/近前台短会话」场景可靠，「锁屏挂机长时间等待被发现」在所有 AOSP 版本上都不可靠（≤15 靠 Doze 之外的 ROM 策略拦截，16+ 靠 importance 门控直接实效化）。

## §2 电池代价

### 2.1 官方文档原文 `[文档]`

AOSP `WifiManager.java`（packages/modules/Wifi main, :8405-8412，与 developer.android.com 参考页一致）：

> "Normally the Wifi stack filters out packets not explicitly addressed to this device. Acquring a MulticastLock will cause the stack to receive packets addressed to multicast addresses. **Processing these extra packets can cause a noticeable battery drain and should be disabled when not needed.**"

注意：官方只说「can cause noticeable battery drain」，**未给出量化值**（任何具体 mA/百分比都 UNVERIFIED）。

### 2.2 代价记账与归因 `[AOSP源码]`

- `acquireLock()` 调 `mBatteryStats.reportWifiMulticastEnabled(WorkSource(uid))`（main :246-247）→ **组播接收的处理耗电记到本 app 的 Wi-Fi 用电名下**（Battery Historian 显示 "Wifi Multicast enabled" 事件；设置→电池的 Wi-Fi 归因可能放大本 app 显示）。
- 全局计数语义：*"if any other Wifi Multicast Locks are still outstanding this release call will not have an immediate effect"*（WifiManager.java:8481-8485 文档原文）→ 若其他 app（KDE Connect 等）已持锁，过滤本就关着，LocalSend 的**增量**电池代价为零。

### 2.3 持锁期=Activity 生命周期的实际代价评估

| 状态 | ≤15 行为 | 16+ 行为 | 电池代价 |
|---|---|---|---|
| 亮屏使用 app（前台） | 锁生效 | 锁生效 | 正当（发现功能所需） |
| 锁屏/home（Activity stopped） | **锁仍生效**（无门控）→ 持续收组播 | 系统实效化锁 | ≤15：真实持续代价；16+：被系统截断 |
| back 退出（onDestroy） | 释放 | 释放 | 终止（但 server 还在跑、组播聋——见 §6） |
| 进程死亡/崩溃 | Binder DeathRecipient 自动释放 `[AOSP源码]`（WifiManager 文档原文 *"when an app exits or crashes, any Multicast locks will be released"*；Multicaster.linkToDeath, main :95-113） | 同 | 终止 |

### 2.4 LocalSend 使用模式下的持有时长 `[推演]`

- **短会话发送**（典型）：打开 app → 选文件 → 发送 → 切回/退出，分钟级 → 持锁分钟级，代价可忽略。
- **长挂接收**（期待场景）：用户开着 app 等别人发 → ≤15 上锁持续生效（组播持续到达，代价持续但换来了「即时被发现」）；16+ 上被门控收敛 → 既省电也意味着不再即时可发现（需要对方主动 /24 扫描兜底，见 §6.4）。
- 传输中的前台服务（flutter_foreground_task, FOREGROUND_SERVICE_DATA_SYNC）：进程 importance 为 foreground service 级（< cached）→ 16+ 门控不触发，**传输期间锁仍有效** `[推演，基于 main 源码 IMPORTANCE_THRESHOLD]`。

## §3 热点/AP 场景（round-1 R-7 环境矩阵「手机热点×笔记本」）

### 3.1 MulticastLock 作用于哪一侧 `[AOSP源码，确定]`

- FilterController 挂在 **ClientModeManager（STA 角色）**上；softAP 由独立的 SoftApManager 管理，不经此路径。
- 手机开热点且 STA 无连接时：`getPrimaryClientModeManager()` 返回 `DefaultClientModeManager`（"used for creating a public ClientModeManager instance **when wifi is off**"，DefaultClientModeManager.java:26），其 `getMcastLockManagerFilterController()` 是 `ClientModeDefaults` 的 default 实现——**空 no-op**（ClientModeDefaults.java:186-193）。
- 推论一：**纯热点模式下 acquire 是无害 no-op**（不崩溃、不生效）。PR-1 无需为此特殊处理 `[推演，源码级]`。
- 推论二：热点+STA 并存（手机同时连别的 WiFi 又开热点）：锁只保护 STA 接口（如 wlan0）的组播接收；ap0/swlan0（softAP 接口）上「STA 客户端（笔记本）→ 手机」方向的组播是否到达内核，取决于驱动/固件对 to-DS 组播帧的处理（hostapd 侧），**与 MulticastLock 无关** `[推演]`；具体 ROM 是否投递 **UNVERIFIED**（未找到一手实测）。
- 佐证（间接）：Windows 移动热点能收 mDNS（Microsoft Learn 2025 案例）说明 AP 侧收组播技术可行但设备相关 `[实测/论坛]`；Apple 个人热点 2015 年报告「广播/组播不进热点网」说明厂商实现差异大 `[实测/论坛]`。

### 3.2 对该场景的结论

PR-1 对「手机热点×笔记本」**大概率无增益也无危害**（锁不作用于 AP 路径）；该场景下 LocalSend 的发现可靠性仍取决于：Rust 侧 per-interface socket 绑定（`packages/core/src/multicast/socket.rs:29-88` 枚举全部接口含 softAP 接口）+ 对端的 /24 兜底扫描（`discovery/mod.rs:296-334`）。这与 round-1 R-7 的判断一致（该场景的主要问题是接口枚举/重绑，不是芯片过滤）。

## §4 特殊设备

### 4.1 Android TV（leanback）

- 同一 `MainActivity` 承载 TV 启动（manifest `LEANBACK_LAUNCHER` 与 `LAUNCHER` 同一 activity，AndroidManifest.xml:59-65）→ 锁逻辑同路径执行 `[仓库事实]`。
- TV 常通电、无电池省电压力，Wi-Fi 通常不开激进省电 → 锁近似 no-op、无害 `[推演]`。
- Android 17 的 `ACCESS_LOCAL_NETWORK` 运行时请求在 `postInit` 中对 TV 同样触发（init.dart:212-220，且 tvProvider 有特判刷新率）`[仓库事实]`。

### 4.2 无 WiFi 只有以太网的 Android 盒子

- `getSystemService(WIFI_SERVICE)` 在无 WiFi 硬件的设备上仍返回 WifiManager 实例（framework 恒注册服务）→ 不返回 null `[推演+AOSP]`。
- acquire 路径走到 `DefaultClientModeManager` 的 no-op FilterController（Android 11+，§3.1 源码链）→ **静默无效果、无异常、无泄漏**。Android 7-10（DefaultClientModeManager 引入前，2020 copyright = Android 11）无 STA 时 native 调用静默失败的细节 **UNVERIFIED**，但无已知 crash 报告（KDE Connect/Syncthing-Fork 的大装机量未爆出此类问题 `[间接]`）。
- 以太网接口的组播不经 Wi-Fi 芯片过滤（内核 IP 栈直接投递给 joined socket，socket.rs:107 `join_multicast_v4`）→ **该形态下组播发现本来就工作，不需要锁**。PR-1 在此类设备上是「无害的多余」。

### 4.3 双频段 / 多网卡

- 单 STA 双频段（2.4G+5G 同时连）非常规；Make-Before-Break 双 STA 时锁跟随 **primary** ClientModeManager，primary 切换由 `PrimaryClientModeManagerChangedCallback` 自动迁移（main :307-330）`[AOSP源码]`。
- 锁无接口粒度（系统级开/关），接口粒度的正确性由 Rust 侧每接口一 socket 负责（socket.rs:20-27 注释）——两层正交，无冲突 `[仓库事实]`。

## §6 策略对比：常持（本 PR）vs 按需 vs server 运行时

### 6.1 前置事实：LocalSend 的 discovery/server 生命周期

- server：app 启动即 `ensureRunning()`（main.dart:68）+ postInit `startServerFromSettings()`（init.dart:224-228）→ **进程级常开**（用户显式关闭除外）`[仓库事实]`。
- discovery listener：postInit 一次性 `StartDiscoveryListener()`（init.dart:232），**全仓无 Stop 调用**（rg 核实）→ **进程级常驻**；多播 announce 由对端触发回答（`set_answer_announcements`，server 不运行时关闭，discovery/mod.rs:381-389）`[仓库事实]`。

### 6.2 权衡表

| 方案 | 复杂度 | 覆盖窗口 | 电池 | 判定 |
|---|---|---|---|---|
| **A. Activity 生命周期常持（本 PR）** | 最低：纯原生层，无跨层通信、无 channel、无竞态 | Activity 存活全程（含 ≤15 的后台期） | ≤15：Activity 不销毁即持续；16+：系统门控自动收敛；BatteryStats 记账到本 app | **合理取舍**（见 6.3） |
| B. 按需 acquire/release（跟随 discovery 启停，KDE Connect 模式） | +1 层：需要 Dart 子 isolate → 主 isolate → 原生 method channel 传递 discovery 状态；引入跨层竞态（channel 丢失/迟到） | 「正在监听组播」窗口 | 最省 | **无意义**：discovery listener 进程级常驻（6.1），窗口≈A，却付出跨层复杂度 |
| C. server 运行时持有（Syncthing-Fork 模式） | +1 层：Dart→原生通知 server 启停 | server 运行期（≈全程，因 server 默认常开） | ≈A（server 几乎总开） | 收益仅在「用户显式关 server」时放手；为小众配置付跨层复杂度，不值 |

### 6.3 论证：常持为何是正确取舍

1. B/C 在 LocalSend 实际架构下的窗口与 A 几乎重合（6.1），精确收益趋近零，复杂度与竞态风险为净增。
2. Android 16+ 的 importance 门控（§1.2）已在系统层实现了「后台自动放手」——A 在新版本上自动获得 C 的电池特性，无需代码。
3. acquire/release 抖动风险：任何「按需」方案在锁边界都有丢包窗口（对端 announce 恰好在 release→acquire 间隙到达）；A 的锁边界仅在 Activity 重建（旋转已由 configChanges 吸收，manifest:48），边界最少。
4. 工程先例背书：Syncthing-Fork 采用「跟随引擎运行期」实质也是「一次 acquire 长持」；KDE Connect 的按需持锁依附于其「discovery 可显式启停」的架构，LocalSend 没有这个结构。

### 6.4 已接受的错配（须在 PR 正文声明，不是 bug）

back 退出（onDestroy）后：锁释放，但 server + discovery listener 仍在 cached 进程中运行 → 本机「听不到」对端 announce（对端设备列表里我将消失/不出现），但**对端主动发送时**的降级路径仍在：对端 `discover_staged` 的 favorites probe + /24 子网扫描（discovery/mod.rs:296-334，SCAN_CONCURRENCY=50、500ms 超时）可通过 TCP/HTTP 发现我（若进程未被冻结/Doze）。即「退出 app 挂后台」的可见性 = 退化为慢路径（数秒 + 大量探测流量）`[推演]`。

### 7.1 KDE Connect（invent.kde.org/network/kdeconnect-android，master 实抓源码）

### 7.2 Syncthing-Fork（Catfriend1/syncthing-android，main 分支 tarball 实抓）

- `SyncthingRunnable.java:130-141`：注释 **"Android 11 blocks local discovery if we did not acquire MulticastLock."**；`createMulticastLock("multicastLock")` + `setReferenceCounted(true)` + acquire，`finally` 中 release（:218-221）→ **跟随 syncthing native 引擎运行期**。同样用 applicationContext。
- 修复史：2021-05-16 PR「Acquire MulticastLock for local discovery to work on Android 11 (fixes #735)」，+15/-0；syncthing 论坛实证 *"Android 11 breaks local discovery. It's fixed in the forked app but the issue isn't solved in the official app yet"* `[实测/论坛]`。

### 7.3 官方 syncthing-android（syncthing/syncthing-android，master raw 实抓）

- **至今无 MulticastLock**（SyncthingRunnable.java grep 零命中）→ Android 11+ 局域网发现持续失效，用户被引导到 fork。**「不加锁的长期代价」的最有力用户实测** `[实测/论坛]`。

### 7.4 对照结论

| App | 锁策略 | 持有粒度 | setReferenceCounted | 依附对象 |
|---|---|---|---|---|
| KDE Connect | 按需 | mDNS discovery 启停 | 默认 true | NsdManager discovery 会话 |
| Syncthing-Fork | 长持 | native 引擎运行期 | true | syncthing 进程 |
| 官方 Syncthing | **无锁** | — | — | （功能失效中） |
| **LocalSend PR-1** | **长持** | **Activity 生命周期** | **false** | MainActivity |

PR-1 与两个持锁先例的本质差异仅在「持有锚点」（Activity vs 引擎 vs 会话），API 用法（applicationContext、tag、幂等 release）与先例完全同款。

## §9 结论

### 9.1 总判定：**PASS（无需改实现即可上游）**

PR-1 的 API 用法与 AOSP 文档语义及两个持锁先例精确同款，且在最坏场景（无 WiFi 设备、纯热点、进程死亡、重复 onDestroy）下经源码级推演全部安全：
- `setReferenceCounted(false)`：首次 acquire 生效、后续 acquire 忽略、首次 release 解锁、后续 release 忽略（WifiManager.java:8507-8536 文档原文）→ onCreate/onDestroy 严格配对 + `isHeld` 双保险，幂等。
- 进程死亡自动释放（Binder DeathRecipient）。
- 无 STA 时 no-op 不崩溃（DefaultClientModeManager 空实现，Android 11+ 源码链）。
- WiFi 重连状态迁移由 framework 负责（primary 切换 callback）。

### 9.2 可选加固（Minor，不阻断）

1. **N-1（建议，一行级）**：`onCreate` 的 acquire 包 try-catch：`WifiManager.acquire()` 内 `e.rethrowFromSystemServer()` 会把 system_server 侧异常转为 RuntimeException 抛给调用方（WifiManager.java:8456-8462）；若 ROM 的 wifi 服务处于崩溃/死亡状态（GrapheneOS os-issue-tracker #6477 显示此类系统故障真实存在），MainActivity.onCreate 未捕获异常 = **app 启动即崩**。KDE Connect/Syncthing-Fork 均未包（先例不包），发生概率极低，故仅为建议。
2. **N-2（记录不做）**：收到网络切换事件后 re-acquire 以规避 Pixel 2022-09 类平台 bug（issuetracker 247596083）——过度工程，依赖 ROM bug 猜测，不做；PR 正文声明即可。

### 9.3 PR 正文应诚实声明的边界/局限清单（给 PR 写作的直接输入）

1. **作用域**：锁只移除 Wi-Fi STA 侧的芯片组播过滤；**不能**克服 Doze 深度期的网络限制、不能阻止 ROM 对后台进程的联网限制/冻结、对 softAP（手机开热点）路径无作用。
2. **版本分界**（可引用本报告数据）：Android 11 起不持锁则 STA 组播默认收不到（syncthing 生态 2021 年实证，Catfriend1 源码注释原话）；Android 16 起系统在 app 退成 cached 进程后自动恢复过滤（AOSP WifiMulticastLockManager importance 门控）——即后台电池代价在新版本被系统自然限制。
3. **后台行为如实描述**：按 home/锁屏（Activity 未销毁）：≤15 锁持续生效（继续可被发现 + 电池代价持续）；16+ 锁被系统实效化（省电但不再即时可发现）。back 退出后：锁释放，但 server 与 discovery 仍在进程内运行——此时仅能通过对端的 /24 子网扫描（慢路径，数秒）被发现，或从最近任务返回后恢复。
4. **电池**：官方文档明示 "can cause a noticeable battery drain and should be disabled when not needed"（引用原文）；本实现的折中=Activity 生命周期持有（前台使用期付出、退出即停），Android 16+ 另有系统级后台护栏；组播耗电计入本 app 的 Wi-Fi 用电统计（BatteryStats WorkSource 归因）。
5. **不保证投递**：持锁 ≠ 100% 到达率——Pixel 2022-09 更新后存在持锁仍丢 UDP 的平台 bug（issuetracker 247596083，切网触发）；屏幕关省电下组播/广播帧仍受 DTIM 周期延迟；自 2011 年起设备间组播支持就有差异。/24 HTTP 兜底扫描保留在所有场景。
6. **权限披露口径**：`CHANGE_WIFI_MULTICAST_STATE` 为 normal 权限（无弹窗、安装即授予）；AOSP 设置→应用→权限页不显示（无权限组）；Play 商店 2022-07 起不再展示权限列表——**用户侧零新增可见摩擦**，无需 Data safety 变更。
7. **无 WiFi 设备**（以太网 TV/盒子）：acquire 为无害 no-op（AOSP DefaultClientModeManager 空实现）；以太网组播不经 Wi-Fi 过滤，此形态本就工作。
8. **同类先例锚点**（增强 PR 可信度）：KDE Connect（mDNS 按需持锁）、Syncthing-Fork（2021 年为 Android 11 加锁，+15 行）、官方 syncthing-android 因未加锁至今局域网发现失效——三条先例链可直接引用。

### 9.4 验证状态与 UNVERIFIED 清单

- 已核实（源码级）：AOSP main + 12/13/14/15/16 的 WifiMulticastLockManager 行为差异、WifiManager.MulticastLock 全部文档语义、DefaultClientModeManager no-op 链、KDE Connect 与 Syncthing-Fork/官方 Syncthing 持锁源码、本仓 discovery/server 生命周期。
- UNVERIFIED：① MIUI/HyperOS、EMUI/HarmonyOS、OneUI 上组播到达率的一手实测报告（仅间接证据）；② Android 7-10 无 WiFi 设备上 acquire 的确切行为（无 crash 报告但源码未追）；③ STA→softAP 方向组播投递的驱动行为；④ 电池代价的量化数值（官方与实测均无）；⑤ importance 门控的确切引入 commit（tag 比对定位为 16.0.0_r1，15→16 之间未逐 commit 考证）；⑥ MIUI「其他权限」页是否展示本权限。
