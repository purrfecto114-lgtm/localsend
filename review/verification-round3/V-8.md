## 2. 验证二：回退字符串与上游类名 —— 实测「不匹配」，但回退依然正确（任务描述有一处事实错误，予以纠正）

命令与证据：

```
$ git show 9529e915:app/lib/provider/local_ip_provider.dart | grep -n "FetchLocalIpAction"
54:  await dispatchAsync(FetchLocalIpAction());
69:  class FetchLocalIpAction extends AsyncReduxAction<LocalIpService, NetworkState>   ← 公有，无下划线

$ git show 9529e915:app/lib/config/refena.dart | grep -n "FetchLocalIpAction"
30:  ActionDispatchedEvent() => ... == '_FetchLocalIpAction',
31:  ActionFinishedEvent() => ... == '_FetchLocalIpAction',
```

结论链：

1. **任务描述称「上游类仍私有」不成立**：上游 9529e915 的类是公有 `FetchLocalIpAction`；fork 1ac3fea3 做的是「字符串修正」（把失效的 `'_FetchLocalIpAction'` 改为生效的 `'FetchLocalIpAction'`），不是「公有化」。
2. 因此 `'_FetchLocalIpAction'` 与上游实际类名**不匹配**（失配一个下划线前缀），任务预期「应匹配」经实测证伪。
3. 但这**不是 PR-2 引入的问题**：上游自己的 refena.dart:30-31 就是 `'_FetchLocalIpAction'`——即**上游这两行排除本来就是失效条件（永远 false，上游既有 bug）**。PR-2 对这两行相对上游零改动（原样继承），行为与上游 9529e915 逐位一致，不引入任何回归。
4. 影响面（Info 级）：`_exclude` 仅被 `CustomRefenaObserver`（debug observer：`RefenaDebugObserver` / `RefenaTracingObserver`）使用 → 字符串失效只导致 debug 日志多记录 FetchLocalIpAction 的 dispatched/finished 事件；release/profile 新增的 `OnChangeEnablingObserver` 是 no-op、不经过 `_exclude`，零影响。
5. 判定：回退**安全且是保持 PR 最小边界的正确选择**（若改成 `'FetchLocalIpAction'` 虽能让排除生效，但超出 PR 主题且属上游既有 bug 的顺手修，留给单独 issue/PR 更干净）。建议在 PR 描述中顺带向上游指出该失配。
