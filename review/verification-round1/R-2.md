## 3. Important（应修复）

### I-1 `previousIps.isNotEmpty` 使"空→非空"转换永不重绑（冷启动无网死角，注释与代码不符）

- **位置**：`local_ip_provider.dart:100` `final setChanged = previousIps.isNotEmpty && previousIps.toSet() != newState.localIps.toSet();`
- **机理**：发现起步于无任何可用 IPv4（`NetworkInterface.list()` 空）时，Rust `multicast::start` bail（multicast/mod.rs:263-268），`listen()` 流**不结束也不发自愈事件**（§1.E）——唯一救活方式是 restart。而首轮抓取 previousIps=[]（本应跳过），网络恢复后抓到非空集合时 `isNotEmpty==false` → **依然跳过**。
- **真实环境触发**：
  1. **Windows/Linux 开机自启动**（LocalSend 支持自启动）：应用先于 Wi-Fi 关联/网卡初始化启动 → 首抓为空 → 网络就绪后永不重绑 → 多播永久哑火，直到用户改任意 discovery 相关设置（settings_provider.dart:47 会附带触发）或手动"重启服务器"（settings_tab_controller.dart:149）；
  2. 飞行模式下启动、网线后插、VPN-only 起步后接 LAN；
  3. Wi-Fi 换频段/重关联的中间态：若某次轮询恰好抓到空集（旧地址已消、新地址未生），restart 绑定到空；下一个轮询"空→非空"不再 restart → 死角复现。移动端有 resume 无条件重绑（main.dart:80）兜底，**桌面端（Windows 轮询/macOS/Linux connectivity 流）无兜底**。
- **注释失实**：:96-98 声称"Rebind the discovery whenever the set of local addresses actually changed"——空→非空恰恰不重绑。
- **修复**：跳过条件改用"首个完成的抓取"而非"previousIps 非空"，例如捕获 `final wasInitialized = state.initialized;` 后 `setChanged = wasInitialized && previousIps.toSet() != newState.localIps.toSet();`（首轮 state.initialized=false 自然跳过；此后空↔非空均覆盖）。可选：空→非空时额外发一次 announce。
- **注**：这是"修复不完整"而非回归（基线同样不重绑任何场景），但补丁把"集合变化→重绑"作为卖点，此洞正是最需要的场景之一。

### I-2 Windows 10s 轮询每 tick 调 `getWifiIP()`，重新引入上游为 #78 专门移除的定位权限触发

- **位置**：`local_ip_provider.dart:61-63`（Timer.periodic 10s → FetchLocalIpAction）+ `:119`（reduce 内无条件 `info.getWifiIP()`）
- **上游历史取证**（git + GitHub API）：
  - 上游 221f40a9（2025-02-18，"fix(windows): unwanted location permission"）**删除的正是 Windows 上的 `Stream.periodic(5s)` 轮询**，留下空分支并引用 #12/#78——即"周期性 FetchLocalIpAction"被上游判定为 #78 的根因；
  - #78（closed，labels: bug/windows）："I use this program on the Windows platform. But it will always try to get my location"——LocalSend 的 `_getIp` 只调 `getWifiIP()`，故触发源就是它；
  - network_info_plus 7.0.0 Windows 实现：`getWifiIP → query() → WlanOpenHandle → WlanEnumInterfaces → WlanQueryInterface(wlan_intf_opcode_current_connection)`（返回含 SSID/BSSID 的 WLAN_CONNECTION_ATTRIBUTES，属位置敏感 API）→ GetAdaptersAddresses 匹配取 IPv4。有 Wi-Fi 网卡的机器上该调用触发 Windows 位置同意提示/位置图标活动。
- **本补丁行为**：Windows 分支恢复周期轮询（10s），且 FetchLocalIpAction 每 tick 都走 `getWifiIP()`——**等于把上游 221f40a9 的修复倒退回去**（频率从 5s 降到 10s 而已）。补丁注释（:55-59）只引用了 #12/#78 解释"为何不走 connectivity 流"，却没意识到 #78 同时也是"不能在 Windows 周期性跑 FetchLocalIpAction"的理由。
- **真实环境触发**：任何有 Wi-Fi 网卡的 Windows 机器，开着应用每 10 秒一次 WLAN 位置敏感查询；位置权限被拒/未决的用户反复看到提示或位置活动指示。
- **修复**：Windows 轮询路径跳过 `getWifiIP()`（仅用 `NetworkInterface.list()` 原生结果即可支撑"集合变更重绑"；Windows 的 third-party 排序增益见 §6 表——本就依赖 UNVERIFIED 的 AP 态 WLAN 状态）。实现上给 `_getIp` 加 `bool includeThirdParty` 参数，Windows poll 传 false；或 Windows 分支缓存"是否存在 Wi-Fi 适配器"再决定。

### I-3 '.1' 排序修复的核心前提在 Android 12+ 不成立（getWifiIP ≠ Wi-Fi 接口地址）

- **位置**：`local_ip_provider.dart:149-157`（注释断言"The third party result is the address of the active Wi-Fi interface"）；测试 `network_info_provider_test.dart:22-33` 以 192.168.43.1 / 172.20.10.1 为前提
- **证据**：network_info_plus 7.0.0 Android `getWifiIPAddress()`（NetworkInfo.kt:25-40）：`SDK ≥ 31` 走 `connectivityManager.getLinkProperties(activeNetwork)` 取首个 IPv4——是**活动网络**而非 Wi-Fi 接口。开热点时 activeNetwork=蜂窝（Android 开 AP 后通常不能同时做 STA）：
  - 蜂窝有 IPv4（CGNAT 10.x 常见）→ thirdParty=**蜂窝地址** → 新代码以 primary=10.x 排第一 → 展示 IP/二维码/扫描首选全部指向运营商 NAT 段（与补丁意图相反；与基线行为相同，非回归）；
  - 蜂窝仅 IPv6 → thirdParty=null → 回退纯 native 排序，热点网关 192.168.x.1 仍被 `.1` 规则压到非 .1 地址之后（但手机接口数少，一般仍在 top-5 内被扫到，只是不排第一）。
  - Android ≤30 走 `WifiManager.connectionInfo.ipAddress`（AP 模式下返回热点地址的行为依 OEM，UNVERIFIED）。
- **真实影响**：补丁在 **iOS 确定修复**（en0=172.20.10.1，iOS 热点场景的展示 IP/扫描首选确实纠正，与新增测试一致）；**Android 12+ 大概率不修复甚至无效**；Android ≤11 视 OEM 而定。真正让热点子网进入扫描的其实是 maxInterfaces 3→5（见 §6 表）。
- **级别理由**：无回归（旧代码同样把蜂窝地址排第一），但补丁注释与测试表达的效果声明在主流 Android 上不成立，会误导后续维护与上游评审。建议：Android SDK≥31 时对 thirdParty 校验其是否出现在 nativeResult 中（不在则视为无效丢弃），可同时治愈"蜂窝 CGNAT 排第一"的存量问题。

## 5. IP 集合比较逻辑专项

- **Set vs List**：`previousIps.toSet() != newState.localIps.toSet()`（:100）——顺序抖动（OS 枚举顺序变化）不会触发重绑 ✓；仅重排序不重绑 ✓（这正是用 Set 的正确理由，注释 :97-98 成立）。
- **无重绑循环**：restart 链（§1.D）不回触发 FetchLocalIpAction；announce 不改 localIps → 不存在反馈环 ✓。
- **IPv6 / fe80::**：:131 `!ip.contains(':')` 把 IPv6 全部滤出 localIps → fe80 隐私地址轮换、v6 临时地址变化**不会**引起重绑 ✓（Rust 侧 v6 socket 按接口 index 绑定，本就无需按地址重绑）。
- **IPv4 link-local 169.254**：Dart `NetworkInterface.list()` 默认 `includeLoopback:false, includeLinkLocal:false`（network_interfaces.dart:16 未传参）→ 不入列 ✓；但注意 Rust if_addrs 侧**会**枚举到 169.254 适配器并尝试绑多播（interface.rs 无 link-local 过滤）——多播绑定面比 Dart 集合宽，重绑判定与实际绑定面不完全对齐（既有行为，非本补丁引入，Info）。
- **白名单交互**：集合比较发生在**过滤后**列表上——用户改 whitelist → settings onChanged 先 sync+restart（settings_provider.dart:41-49，Rust 侧同规则重绑 ✓），但 localIps 要等下一次轮询/连通性事件才刷新（无主动 FetchLocalIpAction 联动，设置页仅有手动"重启服务器"同时刷 :150）。改白名单后 receive 页 IP 展示最多滞后一个 tick（Windows 10s / 其它平台等 connectivity 事件），Minor-4。
- **窗口期语义**：换网瞬间的中间态（旧消新未生）可能被抓到 → 一次多余重绑；下个 tick 抓到终态 → 再一次重绑。两次突发重绑 + announce 突发（3 个延迟 100/500/2000ms，multicast/mod.rs:45-49），可接受、不震荡。
