## 1. 代码实际行为地基（矩阵推演的依据）

**1a. localIps 排序规则**（app/lib/provider/local_ip_provider.dart:112-174）
- `nativeResult` = dart:io `NetworkInterface.list()`，经白/黑名单过滤、丢弃 IPv6（:131），**无排序、无数量上限**；
- `thirdPartyResult` = network_info_plus `getWifiIP()`；
- 合并去重后 `_rankIpAddresses(primary)`（:169-170）：primary=10 分居首，native 中以 `.1` 结尾=0 分垫底，其余=1 分；package:collection `sorted` 为稳定归并排序。
- 补丁删除了旧版"thirdParty 以 .1 结尾→不设 primary"分支（旧 :117-119），现在 thirdParty **永远**是 primary。

**1b. Rust 多播绑定与排序无关**（packages/core/src/multicast/socket.rs:29-88 + util/interface.rs:101-174）
- `local_interfaces()` 枚举**所有**非环回、过过滤器的接口（interface.rs:111-130），**没有排名、没有 maxInterfaces 上限**；
- 每个 IPv4 地址绑一个 socket（wildcard bind + `join_multicast_v4` + `IP_MULTICAST_IF` 钉死出接口，socket.rs:105-118），绑不上/加组失败的接口仅 warn 跳过（socket.rs:51-55）；
- **结论：设备发现（收/发 announce）覆盖所有接口，Dart 排序完全不影响多播绑定**。排序只影响三件事：① UI 展示的本机 IP（device_info_provider.dart:39 `localIps.firstOrNull`）与 web 分享链接/QR；② /24 兜底扫描选哪些网段（scan_facade.dart:27 `take(maxInterfaces)`）；③ 发送页扫描按钮形态（send_tab.dart:331：≤maxInterfaces 走智能扫描，否则弹窗手动选**单个**网段 :349-353）。

**1c. /24 兜底扫描成本**（packages/core/src/discovery/mod.rs:308-334, 342-379）
- 仅当收藏探测后 1s 宽限期内零确认才升级（:321-328）；对 take(N) 的网段**并行** `try_join_all` 全量 /24（255 主机、`SCAN_CONCURRENCY=50` :33、探测超时=discoveryTimeout 默认 500ms，constants.dart:19）→ 最坏 ~3-5s、仅在用户点扫描或发送页初始化空列表时触发（send_tab_vm.dart:230-233）。

**1d. discovery 重启语义**（packages/localsend_isolates/lib/src/task/discovery/discovery.dart）
- `IsolateDiscoveryRestartAction` → 子 isolate `restartListener()`（:125-135）→ stop → 主循环重新 `read(syncProvider)`（:60）→ 全量重绑 + 完整 announce burst（ANNOUNCE_DELAYS 100/500/2000ms × 每接口，multicast/mod.rs:45-49）；
- Rust 侧设备存储每次重启**重建**（mod.rs:463 `DeviceStore::new()`），但 App 层 nearby 设备表在主 isolate 独立存活（nearby_devices_provider.dart:96-98），**UI 设备列表不丢**；
- 重启窗口内旧实例上仍在跑的扫描结果会被丢弃（事件通道已关，mod.rs:204-206 try_send 丢弃）→ 需重扫（Minor）。

**1e. settings→重启的顺序性主张：成立（核实）**
- settings_provider.dart:30-39 先派发 `IsolateSyncSettingsAction` → `_PublishSyncStateAction` 把新 syncState 发给子 isolate（actions_sync.dart:122-127），随后 :47-49 派发 restart；
- 子 isolate `_handleMessage`（child/main.dart:74-88）对每条消息**先同步**派发 syncState 更新、再 await handler，且 SendPort 消息 FIFO → restart task 执行时 syncProvider 已是新值。补丁 commit message 的顺序性论证正确。

```dart
final parentState = global.read(parentIsolateProvider);      // :102
if (parentState.discovery != null) {
  global.dispatch(IsolateDiscoveryRestartAction());           // :104
```

- 证据③：`dispatch<R>(GlobalActionWithResult<R>)` 只接受 GlobalAction；`IsolateDiscoveryRestartAction` 是 provider 作用域的 `ReduxAction<IsolateController, ParentIsolateState>`（isolates actions.dart:170）→ 类型错误。

- 证据⑤：refena_flutter 3.5.0 = refena 3.5.0 再导出（refena_flutter.dart:1-14，依赖 `refena: >=3.5.0 <3.6.0`），无额外 action 扩展；/tmp 既有 refena 副本与 pub.dev 官方归档逐字节一致。

### Important

**I-1 空集→非空转换永不重绑：`previousIps.isNotEmpty` 守卫写反了场景**（local_ip_provider.dart:100）
```dart
final setChanged = previousIps.isNotEmpty && previousIps.toSet() != newState.localIps.toSet();
```
- 注释（:98-99）声称只跳过"第一次 fetch"，但实现跳过的是**一切从空 IP 集到非空的转换**——恰是"网络在 App 启动后来才可用"的场景：启动时飞行模式/未插网线 → fetch#1 得 `[]` → 开 Wi-Fi → fetch#2：`previousIps` 仍为空 → `setChanged=false` → **不重启**；后续 fetch 集合不变 → 永不重启。
- 此时 Rust discovery 是以"零多播 socket"启动的：`multicast::start` 空接口直接 bail（multicast/mod.rs:263-268），`multicast_error` 置位但**不产生** `SocketsFailed` 事件（该事件只由已绑定 receive loop 全灭触发，mod.rs:299-307）→ listen 流不结束 → 无自愈重启（discovery.dart:114-119 只在流结束后触发）。
- 移动端有 F4 resume 重启兜底（main.dart:70-81）；**桌面端（无 resume 派发）无任何兜底**，用户只能改设置/手动重启服务器按钮（settings_tab_controller.dart:149）或重启 App。
- 修复：改为 `newState.localIps.isNotEmpty && previousIps.toSet() != newState.localIps.toSet()`（或显式"已做过首次 fetch"标志位）。

**I-2 '.1' 降权删除的立论前提在三平台全部不成立（热点主机场景）**
- 补丁注释（local_ip_provider.dart:149-157）与新测试（test:22-32）假设 `getWifiIP()` 在设备**提供**热点时返回热点网关（192.168.43.1 / 192.168.137.1 / 172.20.10.1）。版本钉死的插件源码逐一反驳：
  - **Android 12+**（network_info_plus 7.0.0，NetworkInfo.kt:24-41）：`getWifiIPAddress` 改用 `connectivityManager.getLinkProperties(activeNetwork)` —— 热点主机+移动数据在线时返回的是**运营商 NAT 地址**（rmnet 10.x，非 LAN 地址），离线时 activeNetwork=null 返回 **null**；均不是 192.168.43.1。Android<12：热点下 `wifiInfo.ipAddress=0` → null。
  - **Windows**（network_info_plus_windows.dart:78-105,183-201）：只对 `WlanEnumInterfaces` 枚举到的**物理 WLAN 适配器**且 `isState!=0`（有客户端关联）时取其地址；移动热点跑在 Wi-Fi Direct 虚拟适配器（192.168.137.1），物理 WLAN 无关联 → 返回 **null**。
  - **iOS**（FPPNetworkInfoPlusPlugin.m:70-77,140-165）：只遍历 `en*` 接口取第一个 IPv4；个人热点的 AP 接口（ap0/bridge100）不匹配 `en` 前缀，主机态无 en* IPv4 → **nil**。
- 因此 thirdParty 以 `.1` 结尾且真是热点网关的输入路径**在三平台都不存在**；该改动在热点主机场景是**惰性（无效果）**的，热点网关仍以 native 身份垫底（local_ip_provider.dart:169 score 0）。新增的两个"hotspot gateway"测试在机械上可通过（纯函数断言正确），但编码的是现实中不可达的输入——不能作为热点修复的覆盖证明。
- 无回归：受影响的仅剩"Wi-Fi 客户端自身地址恰以 .1 结尾"的罕见网络，此时新行为（active 接口居首）反而更正确。R-6 的"Android 热点效果 UNVERIFIED"至此升级为**带插件源码证据的 VERIFIED-negative（三平台）**。
- 修复建议：把 F2a 的对外表述从"热点网关优先"改为"活动 Wi-Fi 接口不再被 .1 启发式误降"；热点网关优先若真要做，需在 native 侧识别热点接口名（上游 2023 年废弃 spike `feature/improve-local-ip-ranking` 即此路线，R-6 已核实）。

## 3. 六类真实环境矩阵推演

### E1. Windows 11 笔记本：Wi-Fi + 以太网 + Cisco AnyConnect + Hyper-V vSwitch + WSL2 NAT
接口画像（典型 5-7 个 IPv4）：Wi-Fi 192.168.0.52、以太网 192.168.1.50、VPN 10.8.x.x、vEthernet(Default Switch) 172.28.x.1、vEthernet(WSL) 172.20.x.1、热点启用时 +192.168.137.1。
- **多播绑哪些**：Rust 绑**全部**（interface.rs 无上限无排序）——含 VPN（announce 入隧道）与两个 vSwitch（无害）；单接口绑失败仅跳过（socket.rs:51-55）。
- **发现走哪条路**：多播为主（全接口）；静默时 /24 兜底= take(5)。
- **10s 轮询成本**：见 N-1，可忽略；VPN 断连/重连 → 集合变化 → 重启 1-2 次，可接受。
- **补丁收益**：F2b+F2c 让"App 运行中插网线/开热点/连 VPN"在 ≤10s 内重绑——基线在 Windows 上**完全没有**任何网络变化检测（基线 :51-53 Windows 分支为空，见 git show 9529e915），这是真实增益。**但 F2c 因 C-1 不编译，收益为零直至修复。**
- **风险**：6+ 地址时发送页退回手动单网段弹窗（send_tab.dart:331,349-353）——maxInterfaces=5 没有终结该 UX。
- **最坏场景（修复 C-1 后仍存在）**：Wi-Fi+以太网+VPN+vSwitch×2 共 6 地址且用户开移动热点 → 第 7 地址 192.168.137.1 以 native .1 垫底、总长 >5 → **智能扫描的 /24 兜底不含热点网段**；此时靠多播兜住（Rust 全绑）——若热点多播又被防火墙拦，手机在 /24 兜底里扫不到。用户现象：热点上笔记本↔手机时有时无。
- 无感判定：F2a 无感（thirdParty=非.1 客户端地址或 null）；F1 有感（设置即时生效）。

### E2. Android 14 国产 ROM（电池优化激进）：息屏 10 分钟回前台
- **resumed 重绑是否真恢复发现**：进程未被杀 → resume → 重启 → 重绑 + announce 外发 → **对端（桌面/笔记本）收到后 HTTP register 回来 → 本机设备列表恢复** ✓。进程被杀 → 冷启动全量绑定 ✓。被冻结（cached-app freezing）→ 解冻即 resume ✓。
- **MulticastLock 状态**：全仓无锁（N-3）→ **接收方向仍 ROM 依赖**；两台 Android 互发可能双聋。结论：F4 修复"socket 死亡"半边，修不了"驱动过滤"半边。
- **F2c 对"运行中开热点"的覆盖是 ROM 依赖的**：connectivity_plus 7.3.1 Android 用 `NetworkCallback.onAvailable/onCapabilitiesChanged`（ConnectivityBroadcastReceiver.java:44-70，只跟踪**本机客户端网络**）——开热点若伴随 Wi-Fi STA 断开 → 事件触发 → fetch → 集合变化 → 重启 ✓；若移动数据在线且 STA 未断（并发 STA+AP 或本就无 Wi-Fi）→ **无事件 → 不重绑**，只能等 resume。
- **最坏场景**：手机开移动数据、LocalSend 后台活着、开热点给笔记本 → 无 connectivity 事件、无 resume → 笔记本看不到手机，直到用户切一次 App。现象：'热点开了但对方不出现，切出去再回来就好了'。
- 无感判定：F2a 无感（I-2：Android 12+ thirdParty=运营商 IP 或 null——UI 本机 IP 可能显示 10.x 运营商地址，为先存问题）；F3 无感（手机接口数 ≤5）。

### E3. iOS 17
- 原有分支：F4 的 iOS 门是 63efbe6b 既有行为，补丁零改动 → 无回归。
- 交互问题排查：resume 双重启（main.dart:80 + FetchLocalIpAction）良性（N-5）；F1 新作用于 iOS ✓；F2a 惰性（I-2：en* 遍历不含 ap0/bridge100）；新增 iOS 测试用例（172.20.10.1）编码不可达输入。
- 无感判定：除 F1 外全部无感；中性偏正。

### E4. Linux 开发服务器：eth0 + docker0 + 多 br/veth
- **maxInterfaces=5 够不够**：eth0 + docker0(172.17.0.1) + br-a + br-b + br-c = 5 → 刚好全覆盖；6 个 docker 网以上 → 退回手动弹窗。**够用但不富余**。
- **排序会不会被虚拟网桥占据**：docker0/br-* 网关全以 .1 结尾 → native 垫底（score 0）→ take(5) 会把 .1 群体包含在内（当非 .1 地址 <5 时）→ **/24 兜底会扫 docker 网桥**：255×N 个 500ms 探测、SCAN_CONCURRENCY=50 → 约 3-5s 浪费，仅用户主动扫描且静默时发生（mod.rs:321-328）。可接受，非新增痛点（基线 3 个时已扫 2 个网桥）。
- 多播：docker0/br 上 announce → 容器可见（N-2，先存）。
- 无感判定：F2a/b/c 无感或 N/A（Linux 走 connectivity 流、无热点）；F1 有感。

### E5. macOS + UTM/Parallels
- **选错网卡的具体链路**：macOS 插件 `getWifiIP` **硬编码 en0**（NetworkInfoPlusPlugin.swift:23 + `withWifiInterface` 文档"pointer to Wi-Fi interface (en0)"）。纯以太网 Mac（en5）+ Wi-Fi 开但未关联 → thirdParty=null → 排序退化为纯 native：UTM bridge101 192.168.64.1 以 .1 垫底 ✓、Parallels vnic 10.211.55.2 不以 .1 结尾 → **可能排在 en5 以太网之前**（取决于 dart 枚举序）→ UI 本机 IP / web 分享 QR 编码 10.211.55.2 → 对端连不上。此链路**先存且补丁未改变**（thirdParty=null 时新旧代码同路径）。
- 补丁行为：F2a 无感；F3 通常无感（Mac 地址数 2-4）；F1 有感；F2b/c 无关（无 Windows timer；resume 门不含 macOS）。
- 最坏场景：上述 QR 编码虚拟网卡地址，接收方扫码失败——与补丁无关，但环境矩阵必须记录。

### E6. 手机开热点给笔记本（P0 目标场景）
- **热点网关 .1 优先后互发现行为**：如 I-2 所证，thirdParty 从不等于热点网关 → 该"优先"**从未生效**。实际互发现路径 = Rust 全接口多播绑定（与排序无关）+ 笔记本侧 thirdParty=客户端地址（非 .1，新旧代码同样居首）。**两台设备通常能互发现——但靠的是多播，不是本次排序改动。**
- **接收方是热点主机 vs 客户端的差异**：
  - 主机（Android 手机）：热点网关 192.168.x.1 native 垫底但入 take(5)（手机接口少）→ /24 兜底覆盖 ✓；**UI 本机 IP/web QR 可能显示运营商 10.x**（移动数据在线时 thirdParty=activeNetwork=rmnet，I-2）→ 分享链接指向错误地址——先存问题，补丁未修也未恶化。
  - 客户端（Windows 笔记本）：thirdParty=192.168.x.123 居首 → 显示/兜底全正确。
- **App 先开、热点后开**：手机侧 ROM 依赖（E2）；笔记本侧 Windows 轮询 ≤10s 检出新适配器 → F2c 重绑——**这是对上游 #3509（Windows 热点互不可见，R-6 已核实为当天新 issue）的正解，但被 C-1 编译错误整体击穿**。
- 最坏场景：fork main 现状 = 构建失败（C-1）；修复 C-1 后 = Windows 侧热点运行时场景闭环，Android 侧仍依赖 resume。
