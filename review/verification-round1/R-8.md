## 1. 结论速览

**总判定：FAIL（1 Critical / 3 Important / 4 Minor / 若干 Info）。**

补丁的四个修复意图中，"仅当 IP 集合变化才重绑" 这一条**被一行相等性错误反转成了"每次 fetch 都重绑"**：Windows 上 discovery 每 10 秒重启一次，每次重启清空 Rust 设备存储并向全网发 3 个组播 announce、诱发全 LAN register 风暴。其余三个修复（settings 重启、Android resume 重绑、maxInterfaces=5）方向正确，但都汇入同一条 `IsolateDiscoveryRestartAction` 通道，而该通道存在一个**丢失重启的窗口**（补丁新增的三个触发源显著提高了撞上窗口的概率），且 Refena 异步 action 无串行化使并发 `FetchLocalIpAction` 可产生重复重启与旧值覆盖新值。

## 3. Findings

### Critical

#### C-1 `setChanged` 是集合同一性比较，恒为 true → 每次 fetch 都重启 discovery
- **File**: app/lib/provider/local_ip_provider.dart:100
  ```dart
  final setChanged = previousIps.isNotEmpty && previousIps.toSet() != newState.localIps.toSet();
  ```
- **What**: `toSet()` 每次调用都新建 `LinkedHashSet` 实例；dart:core `Set` 不重载 `operator ==`（已对 Dart SDK 源码核实），`!=` 即"不是同一个对象"→ 恒为 true。因此 `setChanged ≡ previousIps.isNotEmpty`。注释宣称的 "A set comparison avoids restarts that would only be caused by re-ranking" 完全落空——不仅排序变化会重启，**毫无变化也重启**。同 commit 的 settings_provider.dart:15 作者自己就在用 `ListEquality` 做深比较，此处却写了裸 `!=`；新增的 3 个测试只测 `rankIpAddresses`，未覆盖此逻辑。
- **触发时序（Windows）**:
  1. t=0 启动：`InitLocalIpAction.after()` → Fetch #0：previousIps=[] → 不重启；state.localIps=[A,B]。
  2. t=10s Timer tick → Fetch #1：previousIps=[A,B]，新列表仍 [A,B]（内容相同）→ 两个新 Set 实例 → `!=` true → dispatch `IsolateDiscoveryRestartAction`。
  3. 子 isolate：stop → 重绑（**新建 `DeviceStore::new()`，core/src/discovery/mod.rs:459-468，Rust 侧已确认设备/通道/日志全部清零**）→ `announce()` 三连发（multicast/mod.rs:45-49：100/500/2000ms）。
  4. 每个 peer 收到 announce 都向本机 HTTP(S) 服务器发 register（discovery/mod.rs:482-488）→ 每条 register 又变成 addDevice 事件。
  5. t=20s、30s…… 无限循环。
- **后果**:
  - Windows：**10 秒周期的全网 announce→register 风暴**；N 台装此补丁的 Windows 设备在 LAN 上产生 ~N×(N-1)/10s 次 register（HTTPS 模式下每次都是完整 TLS 握手 + 客户端证书）；设备明细里的确认日志/多通道积累每 10s 被清空；进行中的 /24 子网扫描被取消；事件通道（容量 16）在每次 stop 时丢弃在途事件（见 M-4）。
  - 非 Windows 平台：每次 connectivity 事件、每次 resume（main.dart:64 → InitLocalIpAction.after()）都会重启——恰好在所有平台重新引入了补丁注释里声称要避免的 #12/#78 式"无谓重启"。
  - 与 I-1 叠加：每 10s 撞一次丢失重启窗口，虽被下一轮掩盖，但每轮都是完整的 stop/announce 周期。
- **Fix**: flutter/foundation 已在 import 列表里（local_ip_provider.dart:5），直接
  ```dart
  final setChanged = previousIps.isNotEmpty && !setEquals(previousIps.toSet(), newState.localIps.toSet());
  ```
  （或 package:collection 的 `SetEquality().equals`）。把该判定抽成纯函数并补单测（现测试文件只测排序）。

### Important

#### I-1 restartListener 存在丢失重启窗口：重绑进行中到达的 restart 被静默吞掉，新配置不生效
- **File**: packages/localsend_isolates/lib/src/task/discovery/discovery.dart:59-135
- **What**: `_runListener` 循环的脆弱窗口 = **从循环顶 `read(syncProvider)`（:60）到 `_discovery = discovery` 赋值（:97）之间**，包含 `await startDiscovery`（:64）、`await multicastError()`（:88）、`await setAnswerAnnouncements()`（:94）以及意外停止后的 1s delay（:119）。此窗口内 `_discovery == null`，`restartListener`（:125-135）走 `else if (!_retryCompleter.isCompleted) { _retryCompleter.complete(); }`（:131-134）——**complete 一个没有任何人 await 的 Completer，等于丢弃**。
- **触发时序**:
  1. t0：用户改 discoveryTimeout → [sync(B), restart#1] 两条消息 → 子 isolate 应用 B，restart#1：`_discovery != null` → stop()。
  2. 流结束 → `_discovery = null` → 循环顶读到 syncProvider=B → `await startDiscovery(B)` 在途（数十 ms）。
  3. t0+50ms：用户改 whitelist → [sync(C), restart#2] → 应用 C；restart#2：`_discovery == null` → completer.complete() → **无人等待 → no-op，restart#2 丢失**。
  4. `startDiscovery(B)` 完成 → discovery 以 B（旧 timeout、旧 whitelist）运行，UI 却显示 C。
  5. 该状态持续到下一个任意触发（再改设置 / resume / IP 变化）——在 C-1 修复后，Windows 上可能** indefinitely**（直到下一次真实 IP 变化）。
- **为什么是补丁放大的**：基线只有 2 个 restart 触发点（iOS resume、手动重启服务器）；补丁新增 settings onChanged、Android resume、IP 集合变化三个触发源，且 settings_tab.dart:472-477 的超时输入框是 **onChanged 逐键触发**——手输 "1500" 在 ~400ms 内产生 4 组 [sync+restart]，第 2~4 个大概率落进前一个的重绑窗口，**最后一个（最终值）丢失时 discovery 实际跑的是中间值**（如 150ms），用户可见"改了不生效"，正是补丁要修的原 bug 的复活形态。
- **Fix（任选其一，推荐 a）**:
  a. 版本号/待处理标志：`restartListener` 在 `_discovery == null` 分支改设 `_restartPending = true`；`_runListener` 在 `_discovery = discovery` 赋值后检查该标志，为真则立刻 stop 再循环一轮。使背靠背 restart 幂等收敛（同时根治 I-3、M-1 的丢失形态）。
  b. 把 `_retryCompleter` 换成"重启版本号"：restart 时 `++_restartVersion`；循环在 startDiscovery 返回后比对版本，不一致即再来一轮。

#### I-2 并发 `FetchLocalIpAction`：Refena 无串行化 → 重复 restart + 旧结果覆盖新结果
- **File**: app/lib/provider/local_ip_provider.dart:61-63（Timer 不等待回调完成即再触发）、:84-108（action 内先快照 previousIps、后 `_setState` 最后完成者胜）
- **What（已核实 refena 3.5.0）**: `ReduxNotifier` 对异步 action **没有队列**（redux_notifier.dart:283-398；库注释 :345-357 自认此竞态）。`Timer.periodic` 的回调 `(_) async { await dispatchAsync(...); }` 不会被 Timer 等待；`settings_tab_controller.dart:150` 的手动 Fetch 与 tick 也可重叠；非 Windows 平台 connectivity 事件本身会连发。
- **触发时序**:
  1. t=0：tick → Fetch X 启动，快照 previousIps=[A]；`getWifiIP()` 挂起 12s（Windows 无线接口 WMI 慢/失败——正是注释引用的 #12/#78 环境，UNVERIFIED 具体时长分布）。
  2. t=10：下一 tick → Fetch Y 启动，快照仍 [A]（X 未写回）；此刻用户开了热点，Y 1s 后返回 [A,H]。
  3. t=11：Y 完成 → setChanged（[A]≠[A,H]）→ restart；state=[A,H]。
  4. t=12：X 用**旧快照** [A] 完成 → `_setState([A])` → **state 回退**；X 的 setChanged 按它自己的快照判定（修复 C-1 后为 false，不再触发 restart，但状态已被回退）。
  5. t=20：下一 tick Fetch Z：previousIps=[A] vs [A,H] → 又判"变化"→ **伪 restart**。
- **后果**: 状态回退-再纠正的震荡 + 伪重启；今天就存在但被 C-1 的"恒重启"掩盖（表现为重复 restart 撞 I-1 窗口）；修复 C-1 后会成为剩余抖动源。
- **Fix**: single-flight——`LocalIpService` 持有 `Future<void>? _fetchInFlight`，tick 时 in-flight 则跳过（或排队最后一次）；或给每次 fetch 发单调版本号，完成时版本落后则丢弃不 `_setState`。

#### I-3 settings onChanged 无去抖 + 超时输入框逐键触发 → restart 风暴
- **File**: app/lib/provider/settings_provider.dart:21-49；app/lib/pages/tabs/settings_tab.dart:472-477
- **What**: `onChanged` 对 4 个字段的**每次** state 变化都 dispatch sync+restart 两个 action；超时输入框是 `onChanged`（每键一次）。输入 4 位数 = 4 组消息对在数百 ms 内涌入子 isolate。
- **触发时序**: 见 I-1 第 5 点（"1500" 键入时序）。每组 restart 都伴随一次 stop/rebind/announce 三连发——即使全部生效，也是 4 次完整 announce 突发。
- **后果**: LAN 侧突发放大 ×4；同时高概率踩 I-1 窗口造成终值丢失。
- **Fix**: onChanged 内对 restart 加 300ms 去抖（Timer 取消重排）；并把 settings_tab.dart:472 的 `onChanged` 改 `onSubmitted`。若采纳 I-1 的修复 a，则风暴自动收敛为一次有效重绑，去抖变为锦上添花。

### Minor

#### M-1 Android/iOS 每次 resume 双重启（resume restart + fetch restart 同 tick 竞争）
- **File**: app/lib/main.dart:64（InitLocalIpAction → after() → FetchLocalIpAction）、:70-81（显式 IsolateDiscoveryRestartAction）
- **时序**: resume → 同一事件循环内先 dispatch InitLocalIpAction（其 after() 异步启动 Fetch），紧接着 dispatch restart#B；Fetch 完成后若集合变化（C-1 下恒真）再 dispatch restart#A。两个 restart 间隔 = fetch 耗时（百 ms 级），常落在彼此的重绑窗口内。
- **后果**: 每次 resume 两次 stop/announce 周期（其中一次常被吞）；C-1 存在时 Android 每次 resume 必然双份。修复 I-1(a) 后天然幂等；也可在 resume 路径仅依赖 fetch 的变化检测（fetch 无变化时仍需 restart#B 兜底 socket 失活，故不能简单删掉一个）。
- **级别理由**: 后果被 I-1 修复覆盖、无独立数据损害 → Minor。

#### M-2 `sendWrappedTaskAndListenStream` 的 microtask 发送 vs restart 的同步发送可反序
- **File**: packages/localsend_isolates/lib/src/isolate/parent/actions.dart:565-573（`Future.microtask(() => sendToIsolate(...))`）vs :178-185（restart 在 reduce 内同步 `sendToIsolate`）
- **时序**: 同一同步代码块内先 dispatch 扫描类 action（listen/staged/subnet，走 microtask 延迟发送）再 dispatch restart（立即发送）→ 子 isolate 先收到 restart 再收到扫描任务 → 扫描 handler 执行时可能正处于重绑窗口（`_discovery == null`）→ discovery.dart:180-183 "Discovery is not running, skipping staged discovery" → **本次扫描被静默跳过**。
- **现实可达性**: 现有调用点没有同 tick 组合（init.dart:232 的 listen 在启动期、无并发 restart）→ **UNVERIFIED（理论边缘）**。修复 I-1(a) 顺带消除；或统一两条发送路径。

#### M-3 `_interfacePollTimer` 生命周期残留（dev/边缘）
- **File**: app/lib/provider/local_ip_provider.dart:24, :60-63
- 顶层全局 Timer，无任何 dispose 钩子取消：`ReduxProvider` 非 autoDispose、app 生命周期存活 → 生产路径无泄漏；resume 重复派发 InitLocalIpAction 会 cancel+重建 → 无累积。残留风险仅：热重载后旧闭包持有旧 action/notifier（与既有 `_subscription`:23 同款模式，dev-only）；`IsolateDisposeAction`（detached）后 Timer 仍会 tick 几次，向已 kill 的 isolate `SendPort.send` 是静默 no-op，且 detached 后主 isolate 即将退出。→ Info 级实质，因清单点名而记 Minor/Info 边界。

#### M-4 Rust 事件通道 try_send 丢弃语义被补丁放大（pre-existing，amplified）
- **File**: packages/core/src/discovery/mod.rs:189-209（`found()` 满即丢 Discovered/Updated）；packages/core/src/multicast/mod.rs:299-308 + discovery/mod.rs:490-494（SocketsFailed→MulticastFailed 同样 try_send）；packages/localsend_isolates/rust/src/api/discovery.rs:192（容量 16）
- **丢弃的是什么**：
  - `Discovered/Updated`（设备确认）：设备已进 Rust store 但 **Dart/UI 永远收不到该事件**——UI 无 `devices()` 轮询兜底（全仓仅 deviceLogs 用于详情页），需等下一次确认（下一轮 announce/扫描）才出现。心跳性质的 Updated 丢失无害；首次 Discovered 丢失 = 设备迟到。
  - `MulticastFailed`：若被丢，`listen` 流不结束（api/discovery.rs:256-275 只靠该事件 break）→ Dart 侧 `_runListener` 卡在 await for → **自动重绑永不发生**，组播永久失聪直到外部 restart 触发。这是"控制信号与数据争同一个 16 槽通道"的结构性弱点。
- **补丁的影响**: restart 频率上升（C-1 下 Windows 每 10s）→ 每轮 restart 触发 announce 三连发 → 全 peer register 涌入 → 事件爆发密度上升 → 丢弃概率上升，且每次 stop 都整段丢弃在途事件 + 清空 store。
- **Fix（上游向）**: MulticastFailed 走独立控制通道（oneshot/专用 mpsc，不与数据竞争）；或 restart 完成后从 Rust store 做一次 `devices()` 快照重同步，自愈被丢的 Discovered。

### Info

- **N-1（清单 3-IPv6）不存在**：`_getIp` 过滤含 ':' 的地址（local_ip_provider.dart:131），IPv6 临时地址轮换不影响集合。但**双源合并抖动存在**：`getWifiIP()` 间歇失败（ip=null → rankIpAddresses 走纯 native 分支）通常不改变集合（WiFi IP 一般也在 native 列表），可若 third-party 返回了 native 没有的地址（部分 VPN/热点形态），间歇成功/失败会令集合成员抖动 → 每 flap 一次 restart。建议 Windows 上要求变化连续两次 poll 保持才重绑（hysteresis）。
- **N-2（清单 5）不存在撕裂读**：`NetworkState` 整体替换（local_ip_provider.dart:85-91,:108），UI 读到的是旧或新整体；唯一"半更新"形态是 I-2 的 last-writer-wins 回退。
- **N-3（清单 8）顺序假设成立**：证据链见 §2 第 2 条。真正风险不是顺序而是 I-1 的窗口 + handler 并发执行（child/main.dart:63-65 `_handleMessage` 不被 await，各 task handler 可重叠运行；restartListener 本身同步且不读 syncState，故不受重叠影响）。
- **N-4 启动期 sync 丢失窗口（pre-existing）**: `_PublishSyncStateAction` 对 null 连接器静默跳过（actions_sync.dart:122-127）；`IsolateSetupAction` spawn 期间（约百 ms）的设置变更既发不进 discovery isolate，也被新守卫跳过 restart。窗口极小、仅启动期。
- **N-5**: `IsolateDisposeAction` 只 kill isolate 不清空 `state.discovery` 连接器（parent_isolate_provider.dart:99-107），此后向其 sendToIsolate 均为死端口静默丢弃——本补丁所有 restart 调用点在 detached 后均无害化，无行动必要。
