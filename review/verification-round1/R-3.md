
**结论（问题 1 答案）**：maxInterfaces 只截断 Dart 侧回退扫描的接口列表；多播层的 socket 数 = 接口 IPv4 地址数 + 有 IPv6 的接口数，双栈齐上（IPv6 组 `ff12::fd3a:e420`，api/discovery.rs:199 硬编码），与 3→5 无任何关系。回退扫描阶段每接口 0 个常驻 socket（按需 HTTP 连接）。

## 2. 选择逻辑：>5 个网卡时选哪 5 个（问题 2 答案）

排序规则（local_ip_provider.dart:167-173，`sorted()` 为稳定归并）：
1. score 10：第三方 `getWifiIP()` 结果（活动 Wi-Fi/热点网关）
2. score 1：其余全部，**保持 Dart `NetworkInterface.list()` 的 OS 枚举顺序**
3. score 0：以 `.1` 结尾的地址垫底

**核实：Dart SDK 不排序**。`NetworkInterface.list()` 是 external（sdk/lib/io/socket.dart:222），VM 实现直接用 `getifaddrs()`（runtime/bin/socket_base_posix.cc:373）/`GetAdaptersAddresses`（socket_base_win.cc:357），全部 socket_base*.cc / socket.cc 无任何 sort；API 文档亦未承诺顺序。Rust 侧 if_addrs 同样裸枚举（但其顺序只影响日志，不参与选择）。

**去理想化推演（6+ NIC Linux 开发机）**：eth0 10.0.0.5、wlan0 192.168.1.20（活动→primary）、tailscale0 100.101.102.103、VPN 10.8.0.6、docker0 172.17.0.1、virbr0 192.168.122.1：
排序 = [wlan0, eth0, **tailscale**, **VPN**, docker0] → take(5) 全取，virbr0 被裁。
`.1` 启发式**碰巧**把 docker0/virbr0/VirtualBox(192.168.56.1)/WSL NAT 网关压到尾部，但对 VPN overlay（100.64/10 CGNAT、10.8.0.x、ZeroTier）完全无效——它们落在 score-1 组，按枚举顺序可排在物理网卡之前。旧值 3 时 [wlan0, eth0, tailscale] 同样含 VPN，即 VPN 入选是**既有**问题，3→5 使入选的虚拟/overlay 网段**净增 2 个**（典型即 docker0 + 另一 overlay）。

**边际成本（问题 2 后半）**：仅在回退阶段（multicast+favorites 1s 内零确认时）触发：5×255=1275 个 HTTPS register（3 时 765），峰值并发 5×50=250 个 TLS 握手，500ms/探针，按波次约 2.5-3s 墙钟（并发不叠加）。常驻成本为零（不多绑 socket、不发包）。电量影响仅限桌面场景（手机接口数 ≤2-3，不受影响）。

## 3. 失败处理审计（问题 3 答案）

Rust 多播层逐项核实：
- 单接口 bind/join 失败 → `warn!` + 跳过，其余接口继续（socket.rs:51-55, 78-82）——无 panic、无重试（下次 restart 时自然重试）
- 全部接口失败 → `multicast::start` bail（mod.rs:263-268）→ `DiscoveryHandle.multicast = Err` → 发现继续跑 HTTP-only，`multicast_error()` 启动时一次性上报（discovery.dart:88-91 记 warning）
- 运行中 socket 失效：每 socket 容忍 10 次连续收包错误再放弃（multicast/mod.rs:56-58, 350-364，注释明确提到 Windows ICMP 错误浮现在 recv 的行为）；全部 socket 死亡 → `SocketsFailed` → Dart 侧 stream 结束 → 1s 退避后整轮重启（discovery.dart:110-120）
- 发送失败：逐 socket warn 后继续其余接口（multicast/mod.rs:199-203）
- Windows 大量接口 join：每 socket 只 join 1 个组（每接口一 socket），Winsock 旧式"每 socket 20 组"限制不适用；所有 IPv4 socket 以 wildcard+SO_REUSEADDR 共享 53317 端口（socket.rs:97-105，注释自知无 SO_REUSEPORT）；5 个乃至 20+ 接口均无已知的硬限制。**未发现 `set_recv_buffer_size` 调用**（socket.rs:90-123）——Windows UDP 多播丢包的经典因素是接收缓冲，但本协议数据报极小极稀，实际风险低。[本环境无 Windows 实机，以上为源码级结论，UNVERIFIED on-device]

## 4. 去理想化场景核查（问题 4 答案）

- **docker 网桥常驻 Linux 机**：docker0(172.17.0.1) 排尾部，3→5 后在接口 ≤5 时必然入选；回退阶段对 172.17.0.0/24 发 255 个探针 → 无容器地址时 ARP 无响应 → TCP SYN 超时（受 500ms 探针超时约束），浪费但有限。上游 #3400（"docker/bridge 接口导致 CLI 退出"）已被报告者自行撤回，实测 docker0 存在时 CLI 正常。
- **VPN split-tunnel**：多播层 join 全部接口（含 VPN TUN），但多数 VPN 适配器要么 join 失败（→跳过）要么丢弃多播（Tailscale 明确如此）；扫描流量按目的地址路由，split-tunnel 下 VPN 子网探针进隧道、其余走物理口。
- **Windows 热点（#3509 场景）**：热点适配器（Wi-Fi Direct "Local Area Connection* x"，192.168.137.1）是 native 地址、以 .1 结尾 → score 0 垫底。接口 ≤5（eth+wifi+hotspot+Hyper-V+WSL 恰好 5 个）时入选；**一旦再加 VPN 即 6+，热点子网仍可能被裁**（GetAdaptersAddresses 顺序无保证，见 F2）。
- **Android 热点**：已核实 network_info_plus 7.0.0 Android 源码（NetworkInfo.kt:25-44）：API<12 走 `wifiInfo.ipAddress`，`if (interfaceIp != 0)` 才返回 → 热点-only（STA 断开）时返回 **null**，第三方 primary 路径不触发；API≥12 走 `getLinkProperties(activeNetwork)` 的首个 IPv4 → 热点+蜂窝时 activeNetwork=蜂窝，返回的是**运营商 CGNAT 地址**而非热点网关（AOSP 语义支持，UNVERIFIED on-device）。即：Android 上"热点网关排第一"的新排序**基本不生效**，实际收益来自 maxInterfaces=5（native 热点地址 192.168.x.1 仍在 score 0，但手机接口少、必入前 5）+ main.dart 的 resume rebind。

### Info

**F6. "rarely paid for"是近似而非精确**：announce 突发 100ms/500ms/2000ms（multicast/mod.rs:45-49），grace 仅 1s（scan_facade.dart:37）→ 第 3 次广播的应答来不及抑制升级；慢应答的健康网络也会付 5×/24 的代价。上游 #2780 记录此时序问题。既有行为。

## 8. 结论：5 是否合理、是否应动态/配置化（问题 6 答案）

**5 合理，建议保留**：
1. 原值 3 同为无据经验值（2023 年外部贡献引入），5 恰好覆盖当代桌面常态栈（eth+wifi+hotspot+Hyper-V+WSL）；
2. 边际成本被正确约束在回退阶段（+2×255 探针、≤+100 并发、~3s 墙钟、零常驻开销）——补丁注释的成本模型与 Rust 实现逐行吻合，属少见的"注释即真相"；
3. 失败处理健壮（逐接口跳过、全灭降级 HTTP-only、10 次容错、无 panic）。

**不建议配置化**（增加设置面收益低，whitelist/blacklist 已覆盖高级用户），**不建议动态**（按接口数自适应会造成行为不可预测）。**真正的跟进方向是"选哪些"而非"选几个"**：CGNAT/点对点过滤 + 上游 `feature/improve-local-ip-ranking` 式名称打分（需修正其 Windows 热点名匹配缺陷），完成后 5 甚至可以回收到 4。
