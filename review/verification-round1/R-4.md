## 1. 联网核实：上游 63efbe6b 的设计意图（先做，已完成）

### 1.1 Commit 事实（GitHub API 抓取，本地存证 /tmp/63efbe6b.json）

- **63efbe6be27475a7bd4ec5f322d85c1944c8beed**，2026-08-17，作者 Tien Do Nam，`fix: auto restart server on resume`，无关联 PR（直推 main），是基线 9529e915 的祖先（`git merge-base --is-ancestor` 验证）。
- 该 commit 做了两件事，**哲学截然不同**：
  1. **TCP server（可探测 → 条件重启，iOS+Android 双平台）**：新增 `serverProvider.ensureRunning()`，用 loopback 2s 超时的 TCP connect 探测，**只在探测失败时** `_restartDeadServer()`。
  2. **Discovery 组播 socket（"无法探测 → 只能重绑"，但 **iOS-only**）**：`if (checkPlatform([TargetPlatform.iOS]))` + 注释 "The multicast sockets die the same silent way but cannot be probed, so always rebind them."
- **上游 main（今日）仍是 iOS-only**（raw.githubusercontent.com 抓取 `app/lib/main.dart` 现行版核对）；63efbe6b 之后到基线之间 main.dart 仅有 9529e915 一笔改动（API commits 列表核对），lifecycle 段无人再动。

### 1.2 设计意图推断（证据链）

- 动机 issue 高度吻合 **#2422**（"Windows loses discovery of iPhone after app returns from background"，2025-04，open）：iPhone 退后台几分钟再回前台 → Windows 端再也发现不了它，需手动重启 server。其唯一评论（shadybones，2025-05-12）建议 "add code to auto-restart on app focus (**skip if can verify the server is running correctly (self ping?)**)"——63efbe6b 正是这个建议的实现：**能 ping 的（TCP server）就 ping 后按需重启，ping 不了的（组播 socket）才无条件重绑**，且无条件重绑只施加于有实证死亡报告的平台（iOS 挂起会回收 socket，属平台文档化行为）。
- iOS-only 的第二层理由（源码侧）：`core/multicast/mod.rs:153-156` 与 `discovery/mod.rs:101-106` 的注释均以 "iOS reclaims the sockets of suspended apps" 为 `SocketsFailed`/`MulticastFailed` 的原型场景。Android 上，activity 只是 paused/stopped 时进程仍存活，已绑定的 UDP socket 不会被系统失效（Doze 只限网不解绑；被杀则整个进程冷启动）。即 **Android 没有 iOS 那个"静默死亡"问题**——63efbe6b 的 iOS-only 不是疏漏，是按病下药。

### 1.3 我们的扩展是冲突还是补全？

**既非纯冲突也非纯补全，是换了一种病**：
- 本补丁的 Android 理由（main.dart:72-75 注释）是"socket 启动时绑定一次、不跟随网络变化（热点启用、频段切换）"——这**不是** 63efbe6b 治的"socket 死了"，而是"网络拓扑变了、socket 还活着但过时"。这个问题在源码侧确凿成立（见 §2.3），且确实无法用 liveness probe 探测（socket 活着）——补丁注释里提的 "probe-based rebind（multicast echo liveness check）" **同样治不了这个病**（能探测的只有"死了"，探不出"缺了新接口"）。真正对症的仪器是**接口集合比较**，而补丁自己在 local_ip_provider.dart:93-106 已经实现了它。
- 因此判定：resume 重绑在 Android 上是"钝器兜底"，与 set-change 重绑（精准仪器）大面积重叠；其独有价值仅剩 (a) connectivity 事件丢失/冻结期间的静默变化，(b) 激进 ROM 静默杀 socket（UNVERIFIED，见 §5.4）。
- 上游 PR 视角：这与维护者哲学相逆（见 §1.2），且 2026-07-25 起上游有 AI 贡献限制条款（HANDOFF.md 已记录）——上游对话应以 issue 先行。

### 2.2 与 local_ip_provider set-change 重绑的叠加（20-b 交互项）

- Android 上无轮询（Timer.periodic 10s 仅 Windows，local_ip_provider.dart:51-63），叠加源是 **connectivity stream**。
- **双重重启的真实触发序列**（去理想化）：
  - 场景 1（最常见）：用户下拉快捷开关栏启用热点（app 前台 → onPause → inactive，进程活着）→ connectivity 事件在 shade 打开期间到达 → FetchLocalIpAction → set 变化 → **重绑 #A（后台中完成）**；收起 shade → resumed → **重绑 #B**。间隔 1-3s，两次全量 stop/start/announce/清库。
  - 场景 2：App 被冻结（Android 12+ cached freezer / 国产 ROM）期间网络变化、connectivity 事件丢失 → 回前台 resumed → #B 立即触发；~50-300ms 后 FetchLocalIpAction 平台调用返回，set 变化 → **#A 再触发**。
  - 第三次（connectivity 事件恰在 resume 前后同时到）理论上限 3 次，但 A/A' 共享 previousIps 比较状态，实际 ≤2 次。
- **是否"重启风暴"**：否。两层限幅：(a) child 侧 `restartListener` 在重绑进行中（`_discovery == null` 窗口）到达的重启会完成一个无人等待的 stale completer → 无操作（discovery.dart:131-134），重绑中的第二次 stop 也只命中旧实例（幂等，api/discovery.rs:130-137 stop_tx take 后跳过）；(b) 用户操作频率本身有限。**全链路无任何显式去抖/节流**，有效重绑率上界 ≈ 1/(重绑时长 ~50-300ms)。

### 2.3 "socket 绑定一次不跟随网络"的源码验证（补丁动机成立）

- `core/multicast/socket.rs:29-88`：`bind_multicast_sockets` 只在 discovery start 时枚举一次接口；每接口一 socket。
- IPv4 socket **bind 到 0.0.0.0**（:105）但 `join_multicast_v4(group, interface.address)`（:107）与 `set_multicast_if_v4(interface.address)`（:111）**钉死在绑定时刻的接口地址**：
  - 新接口出现（热点 ap0）→ 无 socket → 该网段不可见 ✓（补丁主张成立）
  - 同名接口 IP 变化（DHCP 续租/频段切换伴随换 IP）→ 组成员关系钉在旧地址 → 静默失效 ✓（补丁主张成立；注意**纯频段切换且 IP 不变**时不受影响——失效载体是地址不是频段，main.dart:73-74 注释的 "band switch" 表述略有夸大但方向正确）
- 除重启外全仓无任何路径重枚举接口（全仓 `IsolateDiscoveryRestartAction` dispatch 点：main.dart:80、settings_provider.dart:48、local_ip_provider.dart:104、settings_tab_controller.dart:149——最后一处是手动按钮）。

### 2.4 Android `inactive`/`resumed` 语义与频率差异（联网核实）

- Flutter 官方文档（api.flutter.dev，已抓取原文）："On Android, for instance, when the OS calls **Activity.onPause**, Flutter will enter the **inactive** state, but when Android calls Activity.onStop, Flutter enters the paused state."
- Android 上触发 onPause→inactive→(resume)→resumed 循环的日常事件：**系统文件选择器/SAF（LocalSend 核心发送流程"选文件"每必触发一次）**、通知栏/快捷设置下拉、权限对话框、分屏失焦、PiP。iOS 上呈现文档选择器不触发 resign active，系统告警才触发。**结论：Android 的 resumed 频率显著高于 iOS，且高频场景嵌入在核心使用流程里**——这是本补丁 Android 扩展与上游 iOS-only 决策的最大现实差异。
- 冷启动时首帧前 observer 未注册、`IsolateSetupAction` 在 preInit（init.dart:190）于 runApp 前完成 → resume 回调到达时 `state.discovery` 必非 null，actions.dart:173-176 的 StateError 在正常启动序列不可达。

### Critical

### Important

**I-1. resume 重绑在 Android 上无条件、无去抖，重绑频次嵌入核心流程**
- 位置：`app/lib/main.dart:70-81`
- 问题：iOS-only 时代该分支只在"挂起致 socket 死亡"场景买单；扩展到 Android 后，每次 SAF 文件选择器返回、每次下拉通知栏、每个系统对话框关闭都会触发一次全量重绑（stop 等待全部 socket 关闭 → 重枚举接口重绑 → 3×{100,500,2000}ms announce burst → **Rust DeviceStore 清空**，core/discovery/mod.rs:463）。Android 上仅 paused/stopped 的进程其 UDP socket 并不会失效，多数重绑是"没病也吃药"的空转。
- 真实环境触发：Android 用户在发送页点"发送"→ 系统选文件 → 返回（1 次）；发 5 个文件分 5 次选（5 次）；每次下拉通知栏（各 1 次）。
- 影响：电量/网络扰动小（burst 可被下一次 stop 中止），但设备详情页的确认日志每次被清（见 M-1）、进行中的智能扫描结果可能丢失（见 M-2），且与上游维护哲学相逆（§1.2），作为 PR 提出会被质疑。
- 修复建议（≤15 行）：三选一——
  1. resume 路径复用 set-change 门控：child 侧记录"本次 discovery 绑定时的接口集合"，`restartListener` 增加 `force` 参数，resume 走非 force 比较后跳过；
  2. 父侧去抖：`Timer(500ms~1s)` 尾随合并同一窗口内的多次 dispatch（同时解决 I-2）；
  3. 保守方案：Android 仅在"上次 resume 后发生过 connectivity 事件丢失"或超时（如距上次重绑 >30s）时才重绑。

**I-2. resume + set-change 双重重绑（Android 网络变化场景的常态）**
- 位置：`app/lib/main.dart:80`（无条件 #B）+ `app/lib/provider/local_ip_provider.dart:100-106`（set-change #A）
- 问题：§2.2 场景 1/2 所述，热点切换、冻结期换网等**恰是补丁瞄准的场景**，而它们会触发两次背靠背全量重绑（间隔 50ms-3s，第二次到达时第一次多半已完成 → 完整二次 stop/start/announce/清库）。
- 影响：无正确性损害（自愈），纯浪费 + 二次清库；且暴露 #B 的信息劣势——它连"什么都没变"时也执行。
- 修复：并入 I-2 的去抖；或干脆只保留 #A（set-change 已覆盖所有接口/地址变化），#B 降级为"距上次成功重绑 >N 秒才执行"的兜底。

## 4. 收益/风险判定（本轮核心结论）

| 维度 | 判定 |
|---|---|
| 机制正确性 | ✅ 全链路验证无崩溃/泄漏/双绑路径；重叠重启被 child 侧吸收；Rust `RUNNING_DISCOVERY` + `stop()` 等待关闭 + `SO_REUSEPORT` 三重防双绑 |
