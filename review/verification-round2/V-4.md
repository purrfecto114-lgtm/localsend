## 2. 新问题猎杀（round-2 专属清单逐项）

### 2.1 main.dart 的 `ref`（build() 的 context.ref）在 750ms 后使用是否安全 → **安全（已核实）**

证据链（refena_flutter 3.5.0 + refena 3.5.0 源码）：
- `context.ref` 返回 Expando 缓存的 `WatchableRefImpl`（extension.dart:27-35），持有 `container`（强引用，= RefenaScope 根 State 的 `_container`，scope.dart:297-316，根 scope 随 app 存活）+ `rebuildable`（`ElementRebuildable`，其中 Element 仅被 **WeakReference** 持有，element_rebuildable.dart:30,38-40）。
- 闭包用到的两个方法均为纯容器操作：`read()` → `_ref.read(...)` 不触碰 element（ref.dart:163-171）；`redux()` → `Dispatcher(notifier: ...)`，`debugOriginRef: rebuildable` 仅用于 observer/tracing 日志（ref.dart:196-206 + dispatcher.dart:34,42-47），`notifier.dispatch` 直接作用于容器内 notifier。
- 官方文档明确：*"a [WatchableRef] lives as long as the [RefenaContainer] lives. If the [Rebuildable] (e.g. Widget) is disposed, then [WatchableRef.watch] has no effect except returning the current state"*（ref.dart:110-117）——比闭包用到的 read/redux 更激进的 watch 在 widget disposed 后都不抛错。
- 本例更稳：`LocalSendApp` 是 `const` 根级 widget（main.dart:48），其 Element 在 app 生命周期内永不 dispose；rebuild 时 Element 复用（无 key、同类型）→ Expando 命中同一 `WatchableRefImpl`，新旧闭包捕获的是**同一实例**。即使假想 Element 被 dispose，闭包也不持有 element 强引用，无泄漏、无崩溃。
- 生命周期回调始终拿到最新闭包：`LifeCycleWatcher.didChangeAppLifecycleState` 调 `widget.onChangedState`（life_cycle_watcher.dart:32-34），State.widget 随 rebuild 更新。

**结论：无发现。** Timer 闭包内用该 `ref` 与在 build 内用无差别。

### 2.2 settings_provider 的 `ref`（onChanged 回调参数）在 500ms 后使用是否安全 → **安全（已核实）**

- onChanged 的 `ref` 是每次 state 变化**新建**的 `ProxyRef`（base_notifier.dart:331-344），只持有 `container`、debug 标签与一个 `LabeledReference`（ChangeEvent/provider 对象，proxy_ref.dart:20-30）——**与 widget/element 完全解耦**，无任何 dispose 语义。
- `read`/`redux` 全部代理到容器（proxy_ref.dart:33-73）。500ms 后使用等价于即时使用。
- 每次按键重建 Timer 时闭包捕获的是**最新一次**的 ProxyRef（settings_provider.dart:62-67），旧 ProxyRef 随旧 Timer 取消而失联，无累积。

**结论：无发现。**

### 2.3 模块级 Timer：热重载 / detached 后触发 → **无害（1 条 Info）**

- **热重载（dev）**：Dart 热重载保留 top-level 可变字段值 → 挂起中的 Timer 连同旧闭包存活；旧闭包引用旧代码对象但捕获的是同一个容器级 `ref`（见 2.1，Expando 按 Element 键控且 Element 复用），派发行为等价。仅当开发者改动去抖时长等常量后，已挂起的 Timer 仍按旧参数执行——标准 Flutter 去抖 gotcha，dev-only，无生产影响。
- **detached 后触发**：`IsolateDisposeAction` 只 `isolate.kill()` 不置 null（parent_isolate_provider.dart:99-107）→ 迟到的 Timer 触发时 `discovery != null` 守卫**通过** → `IsolateDiscoveryRestartAction.reduce` 走 `sendToIsolate`（actions.dart:170-189）→ 裸 `SendPort.send`（typed_isolates isolate_helper.dart:23-25）。向已终止 isolate 的端口 send 是 Dart VM 的静默丢弃（长standing 语义，与 R-8 N-5 的结论一致；本版 SDK isolate.dart 的 SendPort.send 文档未逐字写明 dead-port 行为，**doc-quote UNVERIFIED**，行为层面无争议）。不会抛 StateError（该异常仅在 discovery==null 时抛，actions.dart:173-176）。无崩溃、无僵尸。
- **可选的化妆改进（Info N-5）**：detached 分支顺手 `_resumeDiscoveryRebindDebounce?.cancel()`（及 settings 侧同名）可让语义更整洁，非必需。

### 2.4 Android 去抖期间 resumed→inactive→resumed 循环 → **收敛为单次重绑（1 条 Info 边缘）**

- 只有 resumed 分支会 cancel+重排 Timer（main.dart:100-101）；inactive **不**取消挂起 Timer。循环 N 次最终只剩最后一个 resumed 起算的 750ms Timer → **整个抖动窗口恰好一次重绑**。风暴不可能。
- Timer 可能在 app 回到 inactive 时触发：进程仍活、child isolate 仍跑，后台完成重绑 + announce，无害（与 round-1 立即重绑相比只是时点后移）。
- **冻结边缘（Info N-3，UNVERIFIED）**：若 app 在 Timer 挂起期间被 cached freezer 冻结，Dart 事件循环暂停 → Timer 在解冻时才触发；解冻伴随 resumed 事件，两者到达顺序不定 → 最坏 2 次重绑（迟到 Timer 一次 + 新 resumed 的一次），有界且被子 isolate 收敛。静态推演，无法本地实证 Android freezer 时序。

### 2.5 iOS 立即重绑 + 同 tick InitLocalIpAction→Fetch 链（R-8 M-1）→ **仍可能，有害形态已消除；Android 对应行为**

- iOS（未变，按设计保持上游行为）：t=0 派发 `InitLocalIpAction`（main.dart:71，其 after() 异步启动 Fetch，local_ip_provider.dart:92-95）→ 同 tick 立即 `rebindDiscovery()`（main.dart:102-104）→ Fetch ~50-300ms 后完成，set 变化则再派发 #A（local_ip_provider.dart:132-140）。两次 restart 仍可能背靠背。
- 关键差异在子 isolate：#A 若落在 #B 的重绑在途窗口（`_discovery == null`），round-1 = stale completer 吞掉（旧接口配置无限期存活，R-8 I-1/M-1 的核心危害）；现在 = `_restartPending = true`（discovery.dart:166-169）→ 新绑定完成即停（**在 announce 之前**，discovery.dart:111-120）→ 循环用最新配置重绑。终态正确，代价 ≤2 次绑定 + 1 次 announce。
- Android 去抖后：#A（立即）与 #B（750ms）不再同 tick，网络变化型 resume = 间隔 ≥450ms 的两次完整重绑；无变化型（文件选择器等绝大多数场景）= 仅 #B 一次。正确性同上收敛。
