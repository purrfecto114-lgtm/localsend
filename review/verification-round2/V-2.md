### N-1 [Important] 首抓取重叠/抛异常竞态使 I-1 修复落空：`firstFetchDone` 判定被"未完成的首抓取"窃取

- **位置**：`local_ip_provider.dart:108-110`（fetchId/firstFetchDone/previousIps 同为 start 时快照）+ `:123-125`（丢弃）+ `:155-162`（shouldRebindDiscovery）
- **机理**：`firstFetchDone = state.initialized` 在抓取 **start** 时读取。若首个 fetch Y 尚未完成（其写入是 `initialized:true` 的唯一来源），任何后启动的 fetch X 也读到 `false` → X 把自己当作"首抓取"跳过重绑；Y 稍后完成即被 `_fetchId` 丢弃（或 Y 直接抛异常）→ **没有任何 fetch 执行过"非首抓取"路径的重绑判定**，且 `initialized` 已被 X 置 true → 后续抓取集合不变 → 永不重绑。
- **Windows 时序（代码级确定，触发时长 UNVERIFIED）**：
  1. t=0 离线启动（开机自启动先于 Wi-Fi 关联——正是 R-2 I-1 的目标场景）。InitLocalIpAction.after() → Fetch Y（includeWifiIp=true）→ `getWifiIP()` 在 #12/#78 型环境挂起（R-8 I-2 时序同款假设，时长分布 UNVERIFIED）。
  2. t=5 Wi-Fi 连上（192.168.1.42）。
  3. t=10 timer tick（Timer.periodic 不等待回调完成，:72）→ Fetch X（includeWifiIp=false，仅 NetworkInterface.list，快速返回 [192.168.1.42]）。
  4. X：id 检查通过（X=2 为最新）；`firstFetchDone=false`（Y 未写入！）→ **跳过重绑**；写入 `{localIps:[192.168.1.42], initialized:true}`。
  5. t=25 Y 完成 → id(1)≠2 → 丢弃 ✓（版本机制本身正确）。
  6. t=30/40/… poll：集合恒 [192.168.1.42] → 永不重绑。
  7. Discovery：启动时以零接口绑定（`multicast::start` bail，listen 流不结束、无自愈事件——R-2 §1.E 已核实）→ **多播永久哑火**；Windows 不在 resume 重绑门内（main.dart:77 仅 iOS/Android）→ 只能等用户改设置/手动重启服务器/IP 再变化。
- **第二入口（无需挂起）**：首个 fetch 抛异常（`getNetworkInterfaces` 的 `SocketException` 不在 `_getIp` 的 try 内，:179-187）→ `initialized` 保持 false → 下一个抓取同样以"首抓取"身份跳过重绑。离线启动 + 首抓取抛异常 + 重叠窗口内来网 → 同样死局。
- **非 Windows 变体**：connectivity 事件/resume 在首抓取在途时启动第二个 fetch（connectivity_plus 订阅时是否立即回放当前状态 UNVERIFIED）。
- **定性**：**非回归**——9a661080（`previousIps.isNotEmpty`）与基线（无重绑机制）在同一时序下同样不重绑；这是 I-1 修复在"重叠/失败首抓取"窗口的不完整残留。但后果等级 = I-1 原案（永久哑火 + UI 显示正常 IP 的静默故障），故列 Important。
- **修复建议（一行）**：`final firstFetchDone = fetchId > 1 || state.initialized;`（任何非"首个启动的抓取"都走重绑路径）。代价：仅在"网络一直正常 + 首抓取慢"的罕见情形多一次冗余重绑（一次 announce 突发）。或改为 notifier 级 `_firstFetchStarted` 标志在首次 start 时消耗。
