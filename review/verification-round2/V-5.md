## 4. 新发现 [Critical-1]：provider 级 onChanged 在 release/profile 构建中不触发 → P0 修复的 settings 半边是 release 死代码

证据链（每条可复核）：

1. **refena 3.5.0 源码**（~/.pub-cache/hosted/pub.dev/refena-3.5.0）：`BaseNotifier._setState` 只在 `_observer != null` 分支调用 `_onChangedListener`（lib/src/notifier/base_notifier.dart:164-183，注释 "trigger onChanged **after** the ChangeEvent" 位于 observer 非 null 分支内；else 分支仅 `_listeners.notifyAll`）；`_setStateAsRebuild` 同样门控（:210-228）。`_onChangedListener` 只由 `_setupOnChanged` 注册（base_notifier.dart:331-343）。
2. **observer 为 null 的条件**：`RefenaContainer.observer` 是 final（container.dart:135），由构造参数 `observers` 经 `_observerListToSingleObserver` 得出——**空列表 → null**（container.dart:569-571）。
3. **app 只在 debug 传 observer**：app/lib/config/init.dart:149-160 `RefenaContainer(observers: kDebugMode ? [CustomRefenaObserver()] : [], ...)`——`kDebugMode` 在 release/profile 编译期为 false。该行来自上游 commit f6686563（`git log -S` 证实），非 fork 引入；fork 对 init.dart 零改动（`git diff 9529e915 HEAD -- app/lib/config/init.dart` 为空）。
4. **实证（PoC）**：`flutter test reviews/tmp/v5_settings_poc_test.dart`——
   - 容器**不带** observer：`setNetworkWhitelist(['192.168.0.*'])` 后 connector 收到 **0 条消息**（case1 红：`Expected: an object with length of <1> Actual: []`）→ onChanged 完全未触发；
   - 容器带一个 no-op observer：**3/3 绿**，消息序列精确为 `[SendToIsolateData(syncState≠null), (600ms 后) SendToIsolateData(data=DiscoveryRestartTask)]`——sync 立即、restart 500ms debounce 后，顺序符合 commit 依赖的通道 FIFO 前提。

**影响范围**（全部走 onChanged 的 4 个 provider，release/profile 均死）：
- `settingsProvider`（settings_provider.dart:28-70）：**含本 P0 修复的全部**——网络字段 sync（:37-46）+ debounced restart（:61-68）+ null 守卫。用户在 release 构建里改 whitelist/blacklist/multicast/timeout 仍然不生效（原 P0 bug 在 release 复活）。
- `serverProvider`（server_provider.dart:35，alias/port/protocol→server isolate sync）、`securityProvider`（security_provider.dart:13，证书 sync）、`deviceRawInfoProvider`（device_info_provider.dart:27）——上游继承行为，同样 release 失效，值得单独向上游报 issue。
- **不受影响**：P0 修复的另外两半——`FetchLocalIpAction` 的集合重绑（local_ip_provider.dart:132-140，走 action dispatch，不经 onChanged）和 main.dart 的 resume 重绑（widget 回调）在 release 正常。

**修复方向（供主 agent 决策，本轮未实施——只读纪律）**：最低成本 = init.dart:150 无条件传 observer（如 `observers: kDebugMode ? [CustomRefenaObserver()] : [_NoopObserver()]`）；更彻底 = 把 settings→isolate sync 从 onChanged 移入显式 service 调用（消除对 observer 的隐式依赖）；或升级 refena（>3.5.0 是否修复 observer-gating 未检查，见 UNVERIFIED-3）。

## 5. 对"settings observer 测试未做，因仓库无 refena 测试基建"决策的评估

**结论：作为范围取舍可以接受，但陈述的理由不准确；且真正的坑（不带 observer 的测试会 vacuous pass）比"没有基建"更值得记录。**

- **不准确处**：仓库并非没有 refena 测试基建——`ReduxNotifier.test` 在 4 个测试文件中使用（favorites/last_devices/receive_history/selected_receiving_files）。准确的说法是：**该模式到不了 provider 级 onChanged**（refena 源码 redux_notifier.dart:485-495：`ReduxNotifierTester` 直接设 `_state`，绕过 `_setupOnChanged`，onChanged 永不注册）。而能到达 onChanged 的 API——`RefenaContainer` + `ProviderOverride`——是 refena 3.5.0 的公开导出（refena.dart:14/:49），且 override 初始化路径会调用 `internalSetup(_, provider)` 注册 onChanged（container.dart:203 → base_notifier.dart:343）。R-5 round-1 的 UNVERIFIED-3（override 接线）本轮已实证闭环。
- **三个非显而易见的坑**（PoC 踩过全部）：
  1. **必须传 observer**，否则 onChanged 静默不触发——case2/3 会 vacuous pass、case1 会莫名失败，比不写测试更危险（这正是 §4 Critical 的单测化身）；
  2. **test/mocks.mocks.dart 过期**：`PersistenceService` 的 8 个 getter（getAlwaysOnTop / getLocale / getNetworkWhitelist / getNetworkBlacklist / getDestination / getReceivePin / getDeviceType / getDeviceModel）不在生成的 mock 里（逐名 rg 证实），mockito `when()` 无法补桩——未桩化的非空返回在调用点隐式 cast 处先抛 `type 'Null' is not a subtype of type 'bool'`，when() 根本拿不到控制权；
  3. **IsolateConnector 不可构造**（typed_isolates/lib/src/isolate_helper.dart:16 私有构造器）→ 不能 new、不能 extends，但可以 `implements` 手写录制型 fake（R-5 round-1 提议的 `MockSpec<IsolateConnector>()` 走 mockito `extends Mock implements` 亦可绕过，但会再撞坑 2）。
- **最小路径（已实证全绿）**：`/home/z/my-project/reviews/tmp/v5_settings_poc_test.dart`（~110 行，0 lib/ 改动，3 用例 = R-5 round-1 P1 清单原样：变更→[sync,restart] 顺序 / 无关变更 0 消息 / discovery==null 不抛）。结构：手写 `_FakePersistence implements PersistenceService`（noSuchMethod + Symbol 表）+ `_RecordingConnector implements IsolateConnector` + `RefenaContainer(observers: [_NoopObserver()], overrides: [persistenceProvider.overrideWithValue(...), parentIsolateProvider.overrideWithNotifier(...)])`。可直接拷入 `app/test/unit/provider/settings_provider_test.dart` 转正；唯一注意点是 600ms 真实延时等 debounce（可选 fake_async 化）。
- **一个反直觉的连带结论**：鉴于 §4，正确写出的 settings 测试**反而会暴露 release 死路径**（无 observer 变体即红）——补这个测试的价值比 round-1 预估的更高。
