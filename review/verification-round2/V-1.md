## 3. 验证点 1：R-8 I-1 重绑窗口 restart 丢失 → **FIXED**

Round-1 R-8.md:71-82 原文：窗口 = 循环顶 `read(syncProvider)` 到 `_discovery = discovery` 赋值之间，restartListener 走 `else if (!_retryCompleter.isCompleted) _retryCompleter.complete()` —— complete 一个没人 await 的 Completer 等于丢弃；建议方案 a 即 `_restartPending`。主 agent 完全采纳。

修复代码（discovery.dart）：
- `:34-40` `_restartPending` 字段声明 + 注释；

- `:158-169` restartListener 的 null 分支：`if (!_retryCompleter.isCompleted) complete()` + `_restartPending = true`。

### 四分支逐行推演（restart 到达时循环所处位置）

## 4. 验证点 2：R-8 I-3 settings 去抖 → **FIXED**

Round-1 R-8.md:97-102：超时框逐键 onChanged → 每键一次 sync+restart，4 次完整 stop/rebind/announce 三连发；建议 300ms 去抖 + `onSubmitted`。修复采用 **500ms 去抖（保留 onChanged）**：

- `settings_provider.dart:19-22` 全局 `Timer? _discoveryRestartDebounce`（文件级静态，与 app 生命周期同寿，无泄漏问题——进程退出即消亡）；
- `:61-68`：`if (discovery != null) { cancel 旧 Timer; Timer(500ms) { if (discovery != null) dispatch restart; } }` —— **Timer 回调内二次 `discovery != null` 守卫**（:64），防止 500ms 窗口内状态变化（如 detached 后 connector 虽未清但 isolate 已 kill → dispatch 变 no-op，见 N1；守卫不改变该场景结果但方向正确）；
- **sync 不去抖**：`:37-46` 的 `IsolateSyncSettingsAction` 每次立即派发 —— 与注释 :51-53 声明一致（"the sync itself is dispatched immediately, only the restart waits"）。这保证去抖窗口内子 isolate 的 syncProvider 始终持有最新值，restart 到达时直接读到终值，无需回放。
- 未采纳 `onSubmitted` 改造是合理替代：onChanged+去抖在 TV 对话框模式（text_field_tv.dart:45-48，`onChanged: widget.onChanged` 同样逐键）下行为一致，且无需改 UI 组件。

去抖正确性依赖的两条顺序不变量均已核实：
1. `setDiscoveryTimeout` 内 `await _persistence.setDiscoveryTimeout` → `state = state.copyWith(...)`（settings_provider.dart:175-180）。逐键 4 个并发 async 调用的 persistence 写入按 platform channel FIFO 完成顺序回调 → state 更新保序 → 终值为最后按键值。（platform channel 消息按发送顺序处理为 Flutter 标准语义；`SettingsState` 有 dart_mappable 字段级 `==`（settings_state.mapper.dart:288），值不同的 4 次 copyWith 各自触发 `updateShouldNotify` → 4 次 onChanged，与输入序列 1/15/150/1500 一一对应。）
2. restart 的 send 晚于全部 sync 的 send ≥ 最后一次按键后 500ms → SendPort FIFO（**实测 TEST1**）保证子 isolate 处理 restart 时 `UpdateSyncStateAction` 已全部执行。

## 6. 验证点 4：去抖 Timer 闭包捕获 `ref` 在 500ms 后使用 → **SAFE**

`ref` 的真实类型与生命周期（refena 3.5.0 源码，pubspec.lock:1347-1363 钉死 3.5.0）：

1. **类型**：`NotifierProvider` 的 `onChanged` 回调收到的 ref 是 **`ProxyRef`**——`base_notifier.dart:333-344`：每次 state 变化时 `_onChangedListener` 内**新建** `ProxyRef(container, debugLabel, origin)` 并调用 `onChanged(prev, next, onChangedRef)`。
2. **生命周期**：`ProxyRef`（`proxy_ref.dart:20-30`）仅持有 `final RefenaContainer _ref`（容器强引用）+ debug 标签，**不持有任何 provider-scoped / element-scoped 资源**。其 `read`/`redux` 全部无状态代理到容器（proxy_ref.dart:33-41, 63-73）。
3. **容器存活**：`RefenaContainer` 由 `main()` 在 `preInit` 创建（init.dart:149-160）并传给 `RefenaScope.withContainer`（main.dart:43-52），app 全生命周期存活、从不 dispose。`settingsProvider`、`parentIsolateProvider` 均为普通 provider（后者经 `container.set(overrideWithNotifier)` 注册，init.dart:166-188），refena 3.5.0 无 autoDispose 语义（除非显式 family dispose，此处不适用）→ **容器级持久，500ms 后调用安全**。
4. **无 `_onAccessNotifier` 竞态**：该可变字段仅在 `trackNotifier/trackNotifierAsync`（proxy_ref.dart:149-169）调用窗口内非空；onChanged 的 ProxyRef 实例从未进入该上下文，延迟调用时该字段恒为 null → 走纯代理路径。
5. **dispatch 同步**：Timer 回调里 `ref.redux(...).dispatch(IsolateDiscoveryRestartAction())` → `Dispatcher.dispatch`（dispatcher.dart:38-47）同步 reduce（actions.dart:170-189）→ `sendToIsolate` 同步 send。无跨 await 的 state 一致性问题。

结论：与 Riverpod 的 element-scoped ref 不同，refena 3.5.0 的 onChanged ref 是容器代理，**闭包延迟使用安全**。`main.dart:93-104` 的 `rebindDiscovery` 闭包（context.ref 捕获，750ms Android resume 去抖）同理：widget 挂载期间有效，且 detached 后 app 仍在内存（Widget 树未销毁）。

## 7. 新问题排查

**N1（Info）去抖窗口内 app detached → dispatch 到已 kill isolate**
detached → `IsolateDisposeAction`（main.dart:107-111）→ `isolate.kill()`，但 reduce **不清 state.discovery**（parent_isolate_provider.dart:99-107 返回原 state）。若 500ms Timer 在 kill 后、进程退出前触发：`discovery != null` 为 true → dispatch → `sendToIsolate` → 向已死 isolate 的 SendPort 发消息。**实测（TEST2）为静默 no-op、不抛异常**；且 detached 后 main isolate 随即退出，Timer 大概率不触发。无崩溃、无功能损害。建议（非必须）：`IsolateDisposeAction` 顺手 `copyWith(discovery: null, ...)` 让状态自洽。

**N2（Info）local_ip_provider 的 external restart 与 settings 去抖交错 → 最多多一次重绑**
local_ip 的 restart 无去抖、立即派发（local_ip_provider.dart:137-139，`external(notifier._parentIsolateController)` —— external 为 ReduxAction 实例方法，refena-3.5.0/lib/src/action/redux_action.dart:125-147，文档示例即此用法；编译 0 error 证实）。交错推演：t=0 settings sync(新值)+Timer；t=100 IP 变化 → R1 立即重绑**读到的已是新值**（sync 先于 R1 到达，FIFO）；t=500 Timer → R2 重复重绑同值。结果正确，代价 = 1 次多余 announce burst + Rust confirmed-store 清空一轮（重绑后 re-announce 自愈）。IP 变化低频，可接受；若要消除可让两源共用一个去抖 Timer（非必需）。

**N3（Info）settings 去抖（500ms）与 Android resume 去抖（750ms，main.dart:99-104）互不感知**
极端叠加（改设置后 200ms 内 resume）→ 两次 restart，均读最新 sync，最终一致，多一次重绑。同 N2 定性。

**N4（Minor，既有、非本补丁引入）start 失败瞬间的窄竞态**
restart 恰在 `await startDiscovery` **抛异常前**到达（分支 B 的失败子情形）：restartListener complete 的是**旧** completer；startDiscovery 抛出后 catch（discovery.dart:95）**新建** Completer 并 await 新的 → 循环挂起直到下一个 restart 到达（settings 改动 / IP 变化 / resume）。`_restartPending=true` 残留但随下一次循环顶清零，不产生错误绑定。触发窗口极窄（需 start 恰好失败），且任意后续 restart 解开。基线（9529e915）行为完全相同（同样 complete 旧 completer）→ **既有问题，修复未引入也未恶化**；如要根治可在 catch 里检查 `_restartPending` 立即 continue。

**N5（Info）首跑测试 flake**
`network_info_provider_test.dart` 首次运行 `+13 -2`（失败帧 57:7，发生于 pub 依赖并发下载期间）；随后 6 次重跑 + 全量 93/93 全绿。判定为环境性 flake（首次运行时 pub resolve 干扰），非代码缺陷。建议 CI 首跑失败时自动重试一次。

**N6（Info，理论不可达）isolate 启动 await 窗口内的 settings 变更**
`IsolateSetupAction` await 期间（init.dart:190）若 settings 变更：`_PublishSyncStateAction` 的 `state.discovery?` 为 null → 消息不发（但 parent state.syncState 已更新）；restart 被 `discovery != null` 守卫跳过 → 子 isolate 以 `InitialData(syncState)`（在 reduce await **之前**读取，parent_isolate_provider.dart:64-71）启动 → 用旧值。**当前不可达**：该窗口在 `runApp` 之前（init.dart:190 await → main.dart:43 runApp），UI 不存在，用户无法改 settings；且 postInit 在 isolate 启动后。仅当未来有代码在 preInit 期间改 settings 才会成为真缺口。记录备查。

**其他过查项（无发现）**：
- `_restartPending` 与 `_restartRequested` 组合状态机：分支 C 清零语义正确（§3）；补停路径 `:118` 设 `_restartRequested=true` 保证 `:134` 不走 1s delay——补停后的重绑零额外延迟。✓
