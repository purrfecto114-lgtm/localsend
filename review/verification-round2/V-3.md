## 2. Task 2：新竞态猎杀

### H1 「循环顶清零（:71）」与「post-bind 检查（:111）」之间的窗口
- :71→:111 之间的真实挂起点仅 :76/:100/:106 三个 await（bind 窗口本体）——此处到达的 restart 设 pending，在 :111 被检查。**封闭**。
- 任务点名的"post-bind 检查之后、await for 之前"：:111→:126 **无挂起点**（I-B：unawaited 调用不挂起，`await for` 注册流后即挂起），restartListener 在物理上不可能插入。最接近的真实情形 = 挂起于 await for 内部 → `_discovery != null`（:109 已赋值）→ **stop 路径** :151-155 → 流结束 → 下一轮循环顶新鲜读取。**✅ 覆盖（核实成立）**。
- 循环顶清零的正当性：清零只吞掉"在 :71 之前到达"的 pending，而这类 restart 的动机 sync 必然已应用（I-A），:72 的新鲜读取即满足之。清零不吞掉 bind 窗口内到达者（bind 窗口内无清零点）。**逻辑闭合**。
- 逆向核查（pending 能否穿越 :111 存活到 await for 阶段）：pending 写点仅 :169（null 分支，仅当 `_discovery == null`）与 :71/:117（清零）；await for 阶段 `_discovery != null` → 到达的 restart 走 stop 路径**不写 pending**；:111-:124 同步段不可插入。**→ pending=true 不可能存活进入 await for 阶段，不存在"下一轮意外 stop"。✅**

### H2 连续 2 个 restart 都落在 startDiscovery await 中——单 bool 是否足够
两个 restart 均走 null 分支 → `_restartPending = true`（重复置位，幂等）。后果：:111 命中一次 → **一次** stop + **一轮**额外循环 → :72 一次新鲜读取同时包含两个 restart 的动机 sync（均在各自 restartListener 运行前已应用，I-A）。restart 的语义是幂等的"以最新状态重绑"而非携带增量，故**单个 bool 足够，无计数需求**。混合形态（一个在 startDiscovery await、另一个在 multicastError await）同理。**✅ 足够**。

### H3 `_restartRequested` / `_restartPending` 组合状态机与标志泄漏
写/读点全枚举（rg 核实无其他写点）：

  - :118 置位后 :120 的 stop 终结**当前** await for → :136 同轮消费；
  - :153 置位后 stop 无条件 cancel（api/discovery.rs:135）→ 流必终结（含 multicast Err 形态：`wait_stopped` 立即返回，core/discovery/mod.rs:412-416，cancel 仍执行）→ :134-136 消费；

### H4 stop() unawaited：晚于下一轮循环顶的并发与 Rust stop/start 交错
**Dart 侧因果链（关键）**：:120/:154 的 `unawaited(stop())` → Rust `DiscoveryInstance::stop`：`stop_tx.send(())` → `wait_stopped().await`（join 组播监督任务；core/multicast/mod.rs:299-318：cancel → `receivers.shutdown().await` → `sockets.write().clear()` **释放端口**）→ **然后才** `cancel.cancel()`（api/discovery.rs:130-136 的顺序）→ listen select break（api/discovery.rs:262）→ FRB 流 done → Dart await for 退出 → :132/:134/:136 → 循环顶 → startDiscovery。**即：循环顶严格晚于旧 socket 释放**——unawaited 的 stop 未来中唯一可能更晚完成的部分是 RUNNING_DISCOVERY 清理段（api/discovery.rs:430-436），而它有 `Arc::ptr_eq` 守卫：迟到的清理不会误清新实例。
**逃逸口核查（理论）**：await for 若经 `MulticastFailed` 事件（api/discovery.rs:268-273）先于 stop 的 cancel 退出 → 循环顶 startDiscovery 与在途 stop 并发 → Rust `start_discovery` 的 leftover-stop（api/discovery.rs:187-190）串行化兜底：锁 RUNNING_DISCOVERY → take 旧实例 → `previous.stop()`——若 Dart stop 已取走 stop_tx 并持锁等 wait_stopped，则 leftover-stop 阻塞在 stop_tx mutex 上直至 socket 释放；若 Dart stop 尚未执行，leftover-stop 自己完成完整 stop（send + wait_stopped）再绑定。**两种交错下新绑定都严格晚于旧 socket 释放。✅**（触发该逃逸口需在亚秒窗口内凑满 10 次连续接收错误，core/multicast/mod.rs:58——纯理论）。
**幂等性核实（Rust）**：`stop_tx.lock().await.take()` 仅一次 Some（api/discovery.rs:131）→ 二次 stop 跳过 send/wait；`CancellationToken::cancel` 幂等 latched；RUNNING 清理 ptr_eq 守卫（api/discovery.rs:431-435）。**死锁核查**：Dart stop 取 stop_tx（暂态持锁过 wait_stopped）→ 释 → 取 RUNNING；start_discovery 取 RUNNING → 取 stop_tx。stop_tx 守卫在 Dart stop await RUNNING 前已释放；wait_stopped 仅依赖组播任务自身停机 → 无环。✅（静态推演）
